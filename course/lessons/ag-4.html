Agent Skills: expertise loaded on demand

Lesson 4 of The agent toolkit

Your team has ways of doing things: how a slide deck should look, how contracts get checked, how release notes are written. An Agent Skill packs one of those into a folder that an agent can pick up exactly when it needs it, and ignore the rest of the time.

By the end you can

  • Describe what a skill is (a folder with a SKILL.md plus optional scripts, references and assets) and write a valid one.
  • Explain progressive disclosure in three levels and estimate the tokens it saves.
  • Choose between a skill, an MCP server, a rules file and fine-tuning, and write a description that triggers at the right time.
Prerequisites: AG.2 Context engineering: skills are a context-engineering technique, built on progressive disclosure. Helpful but optional: AG.3 MCP, for the comparison near the end.

  2. In the system prompt of every conversation
  3. In an MCP server's tool description

A procedure needed only sometimes is exactly what skills are for. Putting it in every prompt wastes context on the many tasks that have nothing to do with contracts.

What a skill is: a folder of know-how

General-purpose agents know a lot, but not your way of doing things. Before skills, teams had two bad options: paste the same long instructions into the chat every time, or pile every procedure into the system prompt, where they crowd the context on every task (AG.2).

Anthropic introduced Agent Skills on 16 October 2025, for its Claude apps, Claude Code and API, and on 18 December 2025 published the format as an open standard at agentskills.io so that skills work across products. Since then a growing number of agents have added support; as of 2026 that reportedly includes coding agents such as OpenAI Codex, Gemini CLI, GitHub Copilot and Cursor, though how each one finds and uses skills varies, so check its documentation.

A skill is just a folder. The only required file is SKILL.md:

contract-review/
├── SKILL.md        required: metadata + instructions
├── scripts/        optional: code the agent can run
├── references/     optional: docs it reads when needed
└── assets/         optional: templates, images, data

SKILL.md starts with a few lines of YAML “frontmatter” between --- markers, then plain Markdown instructions:

contract-review/SKILL.md

---
name: contract-review
description: Reviews NDAs and supplier contracts against our
  legal checklist and drafts redline comments. Use when the user
  asks to review, check or mark up a contract, NDA or agreement,
  even if they don't mention the checklist.
license: Proprietary
metadata:
  owner: legal-ops
  version: "1.3"
---

# Contract review

## Steps
1. Identify the contract type (NDA, supplier, licence).
2. Read the matching checklist: references/nda-checklist.md
   or references/supplier-checklist.md.
3. Check every clause against it. Quote the clause and mark it
   OK, RISK or MISSING.
4. Run scripts/redline.py on the file to produce a marked-up copy.
5. Reply with a table of findings, most serious first.

## Never
- Give a final legal opinion. Recommend counsel for any RISK item.

The rules for the two required fields are short. name: up to 64 characters, lowercase letters, digits and hyphens only, matching the folder name. description: up to 1,024 characters, saying what the skill does and when to use it. Optional fields include license, compatibility (environment needs such as “requires Python and internet access”), metadata, and an experimental allowed-tools list of pre-approved tools.

Which of these is a valid skill name under the open standard?

  1. Contract_Review
  2. -contract-review
  3. contract-review
  4. contract--review
Names use lowercase letters, digits and single hyphens, can't start or end with a hyphen, and must match the folder name. Uppercase, underscores and double hyphens are not allowed.

Progressive disclosure: three levels of loading

The clever part of skills is not the folder; it is when each part enters the context window. The standard describes three levels:

  1. Level 1, always: at start-up the agent loads only each skill's name and description, about 100 tokens per skill. Just enough to know when a skill might be relevant.
  2. Level 2, when relevant: when a task matches a description, the agent reads that skill's whole SKILL.md. The standard recommends keeping it under about 5,000 tokens (and under 500 lines).
  3. Level 3, only as needed: the instructions point to extra files (a checklist, an API reference) that the agent opens only if this task needs them, and to scripts that it runs. A script's code doesn't need to enter the context at all; only its output does.

Because level 3 is read from disk on demand, Anthropic notes that the amount of material you can bundle into a skill is effectively unbounded.

Worked example

An agent has 40 skills installed. Each has about 100 tokens of metadata and a 2,000-token SKILL.md.

  1. Level 1 for all of them: $40 \times 100 = 4{,}000$ tokens, always loaded.
  2. A task uses one skill: $4{,}000 + 2{,}000 = 6{,}000$ tokens.
  3. Loading every SKILL.md up front instead: $40 \times 2{,}000 = 80{,}000$ tokens, before a single reference file, on every task. That is over 13 times more, and most of it irrelevant to any one task.

Explain like I'm 5

A robot chef has a box of recipe cards. It doesn't read every card every morning. It only looks at the tabs on top: “pancakes”, “soup”, “birthday cake”.

When someone asks for pancakes, it pulls out just the pancake card and follows it. If the card says “see the syrup card”, it grabs that one too. All the other cards stay in the box.

Where it breaks: a chef chooses by reading a one-word tab, but an agent chooses by reading a whole sentence of description, and it can misjudge. A badly written tab means the right card never comes out.

A skill includes a 3,000-line Python script that the instructions tell the agent to run. How much of the script's code enters the context window when the agent runs it?

  1. All 3,000 lines
  2. None necessarily: the agent runs it and reads only the output
  3. The first 500 lines
  4. It depends on the model's size
That is a big advantage of bundling scripts: deterministic work happens in code, and only the result costs context. (The agent can read the code if it needs to, but doesn't have to.)

Skills vs MCP, rules files and fine-tuning

Skills are often confused with their neighbours on the map from AG.1. The quick version: skills are know-how, MCP is connections, rules files are always-on conventions, fine-tuning is built-in habits.

Building blockAddsLoadedExample
Agent SkillProcedures, expertise, scripts, templatesDescription always; the rest when a task matches“Make a slide deck in our brand style”
MCP serverLive access to an outside system (read and act)Tool definitions while connected (or found on demand)Create a Jira ticket; query the sales database
Rules fileConventions for every task in a projectAlways, every session“Use pnpm; never edit generated/”
Fine-tuningChanged default behaviour, style or costBaked into the weightsA small model that always answers in your house tone

They combine well. A release-notes skill can say: “use the GitHub MCP server's list_pull_requests tool for merged PRs since the last tag, group them into Features, Fixes and Breaking changes, and fill in assets/template.md.” MCP gives the agent hands; the skill tells it what to do with them. (An MCP working group has been exploring ways to deliver skills through MCP servers too.) A simple test: if a new teammate would need an account to do it, think MCP; if they would need a how-to document, think skill; if they would need it on every task, think rules file.

Write the description so it triggers. The description carries the whole burden of activation: if it doesn't say when the skill applies, the agent won't reach for it. The standard's guidance:

  • Say what it does and when to use it, in the user's words: “Use when the user asks to review, check or mark up a contract…”.
  • List the situations it covers, including ones where the user doesn't name the topic (“even if they don't mention the checklist”). A little pushy is fine.
  • Keep it to a few sentences, since every installed skill's description sits in every context.
  • Test it with about 20 realistic requests: some that should trigger it and some near-misses that shouldn't (“update the formulas in my budget spreadsheet” for a CSV-analysis skill).

“Helps with contracts” will fire too rarely and too randomly. Note too that agents tend to consult skills only for tasks they can't easily do alone; a one-step request may not trigger a skill even when the description matches.

Your agent must create invoices in your accounting system, following the finance team's naming and approval rules. What fits best?

  1. An MCP server for the accounting system, plus a skill describing the finance team's rules
  2. A rules file only
  3. Fine-tuning only
  4. A skill only; skills can reach any system by themselves
Creating invoices needs a connection to a live system (MCP or another tool). The team's procedure is know-how needed only for this kind of task, so it belongs in a skill. The two work together.

A skill can run code: use it safely

A skill is more than text. Its instructions steer what the agent does, and its scripts/ folder can run on your machine with the agent's permissions. So treat installing a skill like installing software:

  • Install only from trusted sources: your own team, or publishers you would trust with a program.
  • Review before you use anything less trusted: read SKILL.md and every bundled file, check the scripts and what they depend on, and look for instructions that send data to unfamiliar web addresses.
  • Watch for hidden instructions. A malicious skill could tell the agent to leak data or weaken security, the same prompt-injection risk as with MCP tool descriptions (AG.3).
  • Keep the agent's own guardrails on: sandboxing and permission prompts still apply when a skill runs a command. Pre-approving tools in allowed-tools is convenient, so do it only for skills you have reviewed.

Skills also need the ordinary care of any shared code: put them in version control, give them an owner (the metadata field helps), and update them when the process changes, or the agent will faithfully follow last year's rules.

In real practice: teams start with the procedures people already explain over and over: “how we write release notes”, “how to make a deck in our template”, “how to run and read the load test”. A first skill is usually one SKILL.md of 50 to 150 lines. Scripts and reference files come later, when the agent keeps getting a deterministic step slightly wrong (move that step into a script) or the instructions grow too long (split details into references/). Anthropic's own public examples include skills for Word, PowerPoint, Excel and PDF files.

A colleague shares a popular skill from an unknown website. What should you do before installing it?

  1. Nothing; skills are plain text and can't do harm
  2. Rename the folder so the agent can't find it
  3. Turn off all permission prompts so it runs smoothly
  4. Read SKILL.md and every bundled file, check the scripts and any web addresses they contact, and install only if you trust it
Skills can run scripts and steer the agent, so an untrusted skill is like untrusted software. Review it, and keep the agent's permission checks on.
Explain it back · in two or three sentences

Explain progressive disclosure for skills, and why it lets an agent have dozens of skills installed without filling its context window.

Model answer: Skills load in three levels: only each skill's name and description (about 100 tokens) are always in context; the full SKILL.md loads when a task matches the description; extra files are read and scripts run only when the instructions call for them. So dozens of skills cost a few thousand tokens of descriptions, and only the one skill in use costs more.
Check yourself

Which description is most likely to make a CSV-analysis skill trigger at the right times?

  1. “Helps with data.”
  2. “Analyzes CSV and spreadsheet exports: summary statistics, charts, outliers. Use when the user wants to explore, chart or summarize tabular data, even if they don't say ‘CSV’.”
  3. “The best skill. Always use this skill.”
  4. A 3-page description listing every function in the scripts
Good descriptions state what the skill does and when to use it, in the user's terms, and cover indirect requests. Vague ones misfire; “always use” over-triggers; very long ones waste context in every session.

Connect to AG.2: which context-engineering technique are skills a direct application of?

  1. Prompt caching
  2. Compaction
  3. Progressive disclosure: show a short summary first, load details only on demand
  4. Subagents
Skills are progressive disclosure in a folder: descriptions always, instructions when relevant, resources when needed. They keep the context lean while making a lot of know-how available.

“Every task in this repo must use the project's logging helper instead of print().” Where does this belong?

  1. An Agent Skill
  2. An MCP server
  3. Fine-tuning
  4. The project's rules file (AGENTS.md, CLAUDE.md…)
It applies to every task, so it belongs in the always-loaded rules file. Skills are for things needed only sometimes.

What does the open standard require at minimum for a skill?

  1. A folder with a SKILL.md whose frontmatter has a name and a description
  2. A Python script and a JSON manifest
  3. An MCP server
  4. A signed certificate from the publisher
Everything else (scripts, references, assets, license, compatibility, metadata) is optional. That simplicity is a big part of why the format spread.

Key takeaways

  • A skill is a folder with a SKILL.md (YAML name and description, then instructions) plus optional scripts/, references/ and assets/. Introduced by Anthropic in October 2025; an open standard (agentskills.io) since December 2025.
  • Progressive disclosure: descriptions always (~100 tokens each), SKILL.md when a task matches, extra files and script output only as needed.
  • Skills are know-how; MCP is connections; rules files are always-on conventions; fine-tuning is built-in habits. Skills and MCP combine well.
  • The description decides when a skill triggers: say what and when, in the user's words, and test it.
  • Skills can run code: install from trusted sources and review them first.
