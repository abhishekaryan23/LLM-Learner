Starter kit: a server, a skill and a rules file

Lesson 8 of The agent toolkit

Time to build. In five short steps you'll write the three files that cover most real agent setups: an MCP server with one tool, a skill for a chore you repeat, and an AGENTS.md for the repo. Then you'll test them, lock them down, and leave with a one-screen card for choosing the right piece next time.

By the end you can

  • Write and register a minimal MCP server in Python, a valid SKILL.md and a useful AGENTS.md.
  • Test them with prompts that should and shouldn't trigger them, and fix what misfires.
  • Apply a safety checklist and use the "where to use what" card to pick the right tool for a new need.
Builds on: MCP (AG.3), Agent Skills (AG.4) and AGENTS.md & project memory files (AG.5). This lesson only recaps them in a line each and focuses on doing. You'll need Python 3.10+ if you want to run the server yourself; everything else is plain text files.
Warm-up · guess before you learn

Take your best guess. A wrong guess now makes the right answer stick later.

In a Python MCP server, how does the model learn what a tool does and which arguments it takes?

  1. It reads the server's source code
  2. You paste the code into every prompt
  3. The SDK turns the function's name, docstring and type hints into a tool description and input schema
  4. It guesses from the function name only
The client asks the server for its tool list, and the SDK builds each entry from your function's signature and docstring. So the docstring is, in effect, a prompt.

You install a skill. Before any task needs it, what of it sits in the model's context?

  1. Just its name and short description
  2. The whole SKILL.md and every file in its folder
  3. Nothing at all, ever
  4. Only its scripts
That's progressive disclosure: names and descriptions are always visible, so the agent knows the skill exists; the body loads only when a task matches.

Step 1: an MCP server with one tool

The pieces of this kit arrived in about a year. Anthropic open-sourced the Model Context Protocol in November 2024; AGENTS.md appeared in August 2025; Anthropic launched Agent Skills in October 2025 and published them as an open standard that December. Before them, every team glued tools and instructions into its own app in its own way. Now each piece is a small file that many agents understand. Here is how the three plug into one agent:

Recap of AG.3: an MCP server offers tools; an MCP client inside the agent app asks for the list (tools/list) and calls them (tools/call). Our server gives the agent one read-only tool: look up a team note by title.

What each part does:

  • @mcp.tool() registers the function as a tool. The SDK turns the type hints (title: str) into a JSON input schema and the docstring into the description the model reads. Write the docstring for the model: what it does, when to use it, an example value.
  • mcp.run() uses the stdio transport by default: the agent app starts your script and talks to it through standard input and output. For a shared, remote server you would use the HTTP transport instead.

Version note: the official SDK's v2 (July 2026) renamed the server class. Many tutorials show the v1 form, from mcp.server.fastmcp import FastMCP and mcp = FastMCP("team-notes"); the decorator is the same. If your installed version complains, check which one you have.

Try it by hand first. mcp dev notes_server.py opens the server in the MCP Inspector, a small web page where you can list the tools and call get_note yourself. If it works there, any client can use it.

Explain like I'm 5

Imagine a new helper coming to your house. You give it three things.

A note on the fridge with the house rules: "shoes off", "the cat eats at six", "never open the red cupboard". The helper reads it every time it comes in. That's AGENTS.md.

A box of recipe cards. The helper only reads the titles on the tabs until you ask for pancakes; then it pulls out the pancake card and follows it. That's a skill.

A phone with the bakery's number. When it needs to know what bread is in stock, it calls and asks. That's an MCP server.

Where it breaks: the helper re-reads the whole fridge note every single visit, and has a small "counter" where everything it's using must fit. That's why the note stays short and the cards stay in the box.

The model keeps calling get_note with titles like "Standup notes for Monday". What is the best first fix?

  1. Rename the function to x1
  2. Improve the docstring: say titles are short keys and list examples such as 'standup' or 'oncall' (or add a tool that lists titles)
  3. Remove the type hints
  4. Switch from stdio to HTTP
The docstring and schema are all the model sees about the tool. Clear examples, or a list_notes tool, fix most wrong-argument calls.

Step 2: a skill for a repeatable task

Recap of AG.4: a skill is a folder with a SKILL.md file (plus optional scripts, references and templates). Its short frontmatter is always visible to the agent; the body loads only when a task matches. Pick a chore you explain to the agent more than once a month. Ours: writing release notes.

The rules that make a skill work, from the Agent Skills specification:

  • name: up to 64 characters, lowercase letters, digits and hyphens, and it must match the folder name.
  • description: up to 1,024 characters. Say what it does and when to use it, with the words users actually type ("release notes", "changelog"). This one line decides whether the skill ever fires.
  • Body: concrete numbered steps; keep it under about 500 lines and move long reference material into separate files the body points to.

Where the folder goes depends on the tool. Claude Code, for example, reads .claude/skills/release-notes/SKILL.md in a project; other agents that support the standard have their own skills folder. Notice the last step: the skill drafts but doesn't publish. Keep anything with side effects behind a human check.

Your skill never fires when people ask for a "changelog". What should you change first?

  1. Make the body longer
  2. Rename the folder to Release_Notes
  3. Move the steps into AGENTS.md
  4. Add the word "changelog" (and similar phrases users type) to the description
The agent decides from the description alone, before the body is loaded. Uppercase and underscores would also break the name rule.

Step 3: an AGENTS.md for the repo

Recap of AG.5: the rules file loads in full at the start of every session, so it holds only what applies every time. For our small repo, containing the server and the skill:

Three details worth copying:

  1. Commands that run. "Before you finish" gives the agent a way to check its own work.
  2. A real gotcha. With the stdio transport, stray print() output corrupts the protocol messages. A newcomer would never guess it; one line saves an afternoon.
  3. Conventions for the other two files. The rules file says how tools and skills are written here, so the agent extends the kit in the same style. (The skills folder path is this repo's choice; use whatever your tools read.)

If your team also uses a tool that wants its own file name, don't copy the text: point at this file instead, for example a CLAUDE.md whose only line is @AGENTS.md.

Why does the AGENTS.md warn against print() inside tools?

  1. A stdio MCP server uses standard output for protocol messages, so stray prints corrupt them
  2. Python's print() is deprecated
  3. Printing costs tokens in every session
  4. MCP forbids text output of any kind
With stdio, stdout is the wire. Logs belong on stderr. It is a classic "gotcha" line: specific, from real pain, impossible to guess.

Step 4: try it

Don't trust a setup you haven't poked. Write a handful of prompts that should trigger each piece, and some that shouldn't, and watch what the agent does. Most agent apps show tool calls and loaded skills in the transcript.

PromptExpected
"What's in the standup note?"Calls get_note("standup"), answers from the result
"Who is on call this week?"Calls get_note("oncall"): the docstring's examples help it pick the key
"Draft release notes for v1.4"Loads the release-notes skill, follows its steps, shows a draft
"What is a changelog, in general?"Probably answers directly: a question about the idea, not the chore. Loading the skill here is a mild false positive
"Add a delete_note tool"Asks before adding a write tool (AGENTS.md), then runs pytest and ruff before finishing
"What's the weather in Oslo?"None of the three: says it has no weather tool (or uses one it really has)

When something misfires, the fix is usually in the text the model sees:

SymptomLikely fix
Tool never calledCheck it's registered and appears in tools/list; make the docstring say when to use it
Wrong argumentsAdd example values to the docstring; tighten the types; add a "list" tool
Skill never firesPut the users' own words in the description
Skill fires too oftenNarrow the description ("Use only when…")
Rule ignoredShorten AGENTS.md, make the rule concrete, or turn a must-always rule into a hook (AG.7)

Keep these prompts. Rerun them whenever you change a description, a docstring, the rules file or the model: they are a tiny regression eval for your agent, exactly the habit from M4.7.

Why include prompts that should not trigger the skill or tool?

  1. To make the eval longer
  2. Because skills only load on negative prompts
  3. A description that is too broad makes the skill or tool fire when it shouldn't, wasting context and sometimes doing the wrong thing
  4. They test the network connection
Triggering is a classifier made of words. Like any classifier, you check both misses and false alarms.

Step 5: a safety checklist

Your agent now reads files, runs commands and calls a server. Before you share the kit or add more powerful tools, walk through this list:

  • Least privilege. Start with read-only tools. Give each server only the access and scoped tokens it needs; prefer one small server per system over one that can do everything.
  • Confirm destructive actions. Anything that writes, deletes, sends, pays or deploys needs a human "yes". MCP lets a tool declare hints such as readOnlyHint and destructiveHint; clients may use them to ask for approval, but they are hints, not a guarantee. Back them with permission rules.
  • No secrets in text files. Never put keys, tokens or passwords in AGENTS.md, a SKILL.md or a tool docstring. All of them end up in the model's context and usually in git. Use environment variables or a secrets manager.
  • Review third-party servers and skills. Read the code before installing; check who publishes it; pin the version. A skill can ship scripts that run on your machine, and a tool description can hide instructions aimed at the model.
  • Treat fetched content as data. Web pages, emails and documents can contain injected instructions (SY.7). Tools that read untrusted content and tools that can act should not be combined without a human check.
  • Make must-always rules deterministic. Block dangerous commands with a hook or a deny rule, and run the agent in a sandbox or container when it can execute code (AG.7).
  • Log tool calls. Keep a record of what was called, with which arguments, so you can see what happened when something goes wrong.

A popular third-party MCP server would save you a day of work. What do you do before connecting it to an agent that can also send email?

  1. Connect it; popular means safe
  2. Read its code and tool descriptions, pin a version, give it minimal access, and require approval for actions like sending email
  3. Paste your email password into its description so it works faster
  4. Nothing; MCP servers can't affect other tools
Tool descriptions enter the model's context and can steer it, including towards your other tools. Review, pin, limit, and keep a human in the loop for anything with side effects.

Where to use what: your decision card

This is the map from AG.1, now that you've seen every piece. When a new need comes up, find its row:

Where to use what · one screen

The model must know facts from your documentsRetrieval / RAGSY.3

And across all of them: everything competes for the same context window, so context engineering (AG.2) decides what gets in.

Your first week with an agent on a real project, about an hour a day:

  1. Day 1, rules. Write an AGENTS.md: setup, the test command, three gotchas, a don't-touch list. Give the agent a real task and note every correction you make.
  2. Day 2, tighten. Turn repeated corrections into one-line rules. Move any must-always rule (format, never force-push) into a hook or a permission setting.
  3. Day 3, a skill. Write one SKILL.md for the chore you explain most often. Test it with prompts that should and shouldn't trigger it.
  4. Day 4, a server. Wrap one read-only internal API (tickets, docs, metrics) as an MCP server. Try it in the Inspector, then register it.
  5. Day 5, check. Save your try-it prompts as a mini eval, run the safety checklist, and decide what's next: a wiki for your research notes, or subagents for broad searches.
Why this matters in practice: most of the value comes from small, boring files that you keep improving: a rules file that grows one line per mistake, a skill per repeated chore, a read-only server per system. Big frameworks can come later. Teams that start small also find it far easier to see which piece caused a problem when something goes wrong.

"Every answer our support bot gives must quote the current refund policy, which changes monthly." Which row of the card fits best?

  1. Fine-tuning, so the policy is in the weights
  2. A rules file in the repo
  3. Retrieval (or a tool that fetches the current policy), so the model reads the latest text each time
  4. A2A
Facts from your documents that change often belong in retrieval or a live lookup. Fine-tuning would freeze last month's policy into the weights, and a coding rules file isn't seen by a support bot.
Explain it back · in one or two sentences

Your new agent setup has an AGENTS.md, a skill and an MCP server. How does each one reach the model, and why does that difference matter?

Model answer: AGENTS.md loads in full every session, the skill shows only its name and description until a task matches and then loads its body, and the server's tools are listed up front but their results arrive only when the model calls them. Because the context window is shared, always-needed rules go in the small rules file, occasional procedures in skills, and live data behind tools.
Check yourself

Which SKILL.md frontmatter is valid under the Agent Skills spec?

  1. name: Release_Notes in a folder called release-notes
  2. name: release-notes in a folder called release-notes, with a description of what it does and when to use it
  3. No frontmatter; the agent reads the folder name
  4. name: release-notes with a 3,000-character description
Names are lowercase letters, digits and hyphens, up to 64 characters, matching the folder; descriptions are required and at most 1,024 characters.

In notes_server.py, what does the model actually see about get_note before calling it?

  1. The full Python source
  2. The contents of NOTES
  3. Nothing until the first call
  4. The tool's name, its docstring as the description, and an input schema built from the type hints
That listing is all it has to decide when and how to call the tool, which is why the docstring deserves as much care as a prompt.

Tool calling from SY.4 and an MCP server both give the model tools. When is it worth wrapping a tool as an MCP server?

  1. When the same tool should be reusable across many apps or agents
  2. Always; plain function calling is deprecated
  3. Only when the tool needs no arguments
  4. When you want the tool to be secret from the model
Under the hood the model sees tools the same way. MCP pays off when you want one implementation that any MCP-capable client can plug in; a one-off inside your own app can stay a plain function.

Which item from the safety checklist addresses "a web page told my agent to email our customer list to a stranger"?

  1. Put the email password in AGENTS.md
  2. Use a longer skill description
  3. Treat fetched content as data, and require human approval before tools that send or delete
  4. Switch the server to HTTP
That is prompt injection. Separate reading untrusted content from acting, and keep a human check on side effects.

Key takeaways

  • An MCP server is a short Python file: decorate a typed, documented function with @mcp.tool(); the docstring is what the model reads. Test it in the Inspector, then register it.
  • A skill is a folder with SKILL.md: a valid name, a description that says what and when in users' words, and concrete steps.
  • An AGENTS.md holds commands that run, real gotchas, conventions for the rest of the kit, and no secrets.
  • Test with should- and shouldn't-trigger prompts and keep them as a regression eval; run the safety checklist before adding power.
  • Use the decision card: always → rules file; sometimes → skill; outside systems → tools/MCP; must-always → hooks.
