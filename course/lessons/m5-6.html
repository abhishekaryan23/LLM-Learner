Batching & serving metrics

Lesson 6 of Optimization

Serving an LLM to many people at once is a balancing act. Put more requests on a GPU together and the cost per token falls, but each person waits a little longer for every token. This lesson gives you the vocabulary to reason about that trade-off and shows the scheduling trick every modern serving engine uses: continuous batching.

By the end you can

  • Say why prefill is compute-bound and decode is memory-bound, using arithmetic intensity.
  • Define TTFT, TPOT/ITL, throughput and p50/p99 latency, and compute a request's latency and the cost per million tokens.
  • Explain static, dynamic and continuous batching, and read a latency–throughput curve.
Before you start: this lesson uses the KV cache from KV cache & sampling, the idea of a memory-bound operation and PagedAttention from FlashAttention & paged attention, and connects to speculative decoding.

A GPU serves 32 users at once instead of 1, same model. Roughly what happens to each user's speed (tokens per second)?

  1. It drops 32-fold
  2. It stays exactly the same
  3. It drops a bit, while the GPU's total output rises many-fold
  4. It goes up
At small batch sizes, a decode step is dominated by reading the weights, and that read is shared by everyone in the batch. Adding users costs each of them a little time but multiplies total output.

Which part of handling a chat request keeps the GPU's arithmetic units busiest?

  1. Processing the prompt (all its tokens at once)
  2. Generating the answer one token at a time
  3. Tokenizing the text
  4. Sending tokens back over the network
The prompt's tokens are processed in parallel, so every weight that is read gets used for thousands of tokens. Generating one token at a time uses each weight once per read.

Two phases: prefill and decode

Every request goes through two very different phases:

  • Prefill: the whole prompt goes through the model in one forward pass. This builds the KV cache (M1.5) and produces the first output token.
  • Decode: then the model generates one token per forward pass, each time reading the weights and the KV cache, until it stops.

The difference is arithmetic intensity, the FLOPs done per byte read from memory. A forward pass costs about $2N$ FLOPs per token for a model with $N$ parameters, and reading 16-bit weights moves $2N$ bytes. If one pass handles $T$ tokens, the intensity from the weights is

$$\text{intensity} \approx \frac{2N \cdot T}{2N} = T \ \text{FLOPs per byte}$$

For a 2,000-token prompt, $T = 2{,}000$, far above the roughly 156 FLOPs/byte an A100 needs to keep its compute busy (312 TFLOP/s ÷ 2 TB/s). Prefill is compute-bound. In decode with a batch of $B$ requests, each pass handles $T = B$ tokens, one per request. At small $B$, decode is memory-bound, and reading every request's KV cache only adds bytes. So the main lever for decode is batching: share each weight read among as many requests as possible.

This roofline view ignores attention's own FLOPs, the KV-cache reads in the ratio, and imperfect kernels. It's a first-order model, but it explains most of what you see in practice.

The metrics that matter

  • TTFT (time to first token): from the request arriving to the first output token. It covers queueing plus prefill. This is how responsive the app feels.
  • TPOT (time per output token): the average time between output tokens during decode. ITL (inter-token latency) usually means the individual gaps, whose distribution shows stalls that an average hides.
  • End-to-end latency for $n$ output tokens: $\;\text{TTFT} + \text{TPOT} \times (n - 1)$.
  • Throughput: total tokens per second across all users (usually output tokens; some reports count input too, so check), or requests per second.
  • Percentiles: p50 is the median; p99 means 99% of requests do better. Service-level objectives (SLOs) are usually set on the tail, e.g. "p99 TTFT under 2 s", because a user who sends many requests meets the slow 1% often. Goodput counts only the requests per second that meet the SLOs (Zhong et al., 2024, DistServe).
  • Cost per million tokens: what the GPU time costs divided by the tokens it produced.

Worked example

  1. Latency: TTFT = 300 ms, TPOT = 20 ms, answer of 500 tokens: $0.3 + 0.02 \times 499 = 10.28$ s.
  2. Per-user speed: $1 / 0.02 = 50$ tokens/s once the stream starts.
  3. Cost: a GPU rented at $\$2.00$ per hour (an illustrative price) sustains 2,000 output tokens/s across all users. That's $2{,}000 \times 3{,}600 = 7.2$ million tokens per hour, so $\$2.00 / 7.2 \approx \$0.28$ per million tokens.
  4. The lever: double the throughput at the same GPU price and the cost per token halves, which is why batching matters so much.

Batching: static, dynamic, continuous

So we want big batches. The question is how to group requests whose answers have wildly different lengths:

  • Static batching: pick a group of requests and run them until the longest one finishes. Short answers finish early and their slots sit idle; new requests wait for the whole batch.
  • Dynamic batching: the server collects incoming requests until the batch is full or a short timeout passes, then launches it. That handles uneven arrivals, but each batch still runs to completion, so the idle-slot problem remains for generation.
  • Continuous batching (also called iteration-level scheduling or in-flight batching): introduced by Orca (Yu et al., 2022, "Orca: A Distributed Serving System for Transformer-Based Generative Models"). The scheduler decides after every decode step: finished requests leave, waiting ones join.

In their GPT-3 175B experiments, Orca's authors reported up to 36.9× the throughput of NVIDIA FasterTransformer at the same latency. That figure is specific to their setup, but continuous batching is now standard in vLLM, SGLang, Hugging Face TGI and TensorRT-LLM. It pairs naturally with PagedAttention (M5.4): requests come and go every step, so their KV memory must be easy to hand out and take back.

Explain like I'm 5

Imagine every child in town needs a ride to school, and there's only one road.

If each child takes their own taxi, the road fills up with taxis and everyone sits in a traffic jam. That's serving one request at a time: the road (the memory link) is busy, but each trip carries just one passenger.

A school bus uses the same road once and carries a whole crowd. And a smart bus doesn't wait for everyone to reach the last stop: whenever a child gets off, a new one gets on at the next stop. That's continuous batching.

Where it breaks: a fuller bus stops more often, so each child's ride gets a bit slower (higher latency per token), and the bus only has so many seats: the KV-cache memory.

The latency–throughput trade-off

Bigger batches always raise per-token latency a little, because every step has more work in it. But while decode is memory-bound, they raise throughput a lot. Past some batch size the GPU becomes compute-bound, or runs out of memory for KV caches, and the extra latency buys nothing. Explore it with a deliberately simple model:

Playground: how big should the batch be?

Toy roofline model of decode only (no prefill, no queueing, perfect kernels): a 7B model in 16-bit (14 GB of weights) on an 80 GB GPU with 2 TB/s and 312 TFLOP/s, and 0.125 MB of KV cache per context token. Step time $=\max\big(\tfrac{14\,\text{GB} + B \cdot \text{KV}}{2\,\text{TB/s}},\ \tfrac{B \cdot 14\,\text{GFLOP}}{312\,\text{TFLOP/s}}\big)$.

In this model, going from $B = 1$ to $B = 64$ (2,000-token contexts) makes each user's tokens about 2× slower (7.1 → 15 ms) but the GPU's total output 30× higher (140 → 4,267 tokens/s), and the cost per million tokens falls from about $\$4$ to $\$0.13$. Real engines expose this as settings such as the maximum number of concurrent sequences and the fraction of GPU memory reserved for KV cache. Operators pick the largest batch that still meets their latency SLOs.

Two more tricks: chunked prefill and prefix caching

Chunked prefill. When a request with a 4,000-token prompt joins a running batch, its prefill is a big, compute-heavy step. Run it all at once and every other user's next token is delayed, a visible stutter in their stream. Chunked prefill (Agrawal et al., 2023, Sarathi; 2024, Sarathi-Serve) splits the prompt into chunks of, say, 512 tokens and adds one chunk to each decode step. Decode steps are memory-bound and have spare compute, so the chunks ride along almost for free, and inter-token latency stays smooth. Several engines now enable it by default.

Prefix caching. Many requests start with the same tokens: a long system prompt, few-shot examples, or the earlier turns of a conversation. With paged KV blocks (M5.4) the engine can keep those blocks and reuse them, skipping most of the prefill. That cuts TTFT and cost. Many API providers bill cached input tokens at a discount for this reason.

Going further, some systems disaggregate the two phases onto different GPUs (e.g. DistServe and Splitwise, 2024), so compute-bound prefill and memory-bound decode stop competing for the same hardware.

Why this matters in practice: these numbers shape real products and prices. Prefill is efficient batched compute and decode is memory-bound, which is one reason API prices for output tokens are typically several times those for input tokens. Long contexts are expensive mainly because their KV caches crowd other requests out of memory. And a technique that helps at batch size 1, such as speculative decoding (M5.5), may help much less on a busy, well-batched server. Always ask at which batch size a speed-up was measured.
Explain it back · in two or three sentences

Why does continuous batching beat static batching for LLM generation, and what is the trade-off when you raise the batch size?

Model answer: Answers have very different lengths. Static batching keeps finished requests' slots idle until the longest one ends, while continuous batching reschedules after every decode step, so a waiting request takes a free slot immediately and the GPU stays busy. Raising the batch size shares each memory read among more requests, so throughput rises and cost per token falls, but every step does more work, so each user's time per token (and TTFT under load) goes up, until compute or KV-cache memory runs out.
Check yourself

Which of these is usually compute-bound on a modern GPU?

  1. Decoding one token for a single user
  2. Prefilling a 4,000-token prompt
  3. Reading the KV cache during decode
  4. Sampling the next token from the softmax
Prefill processes thousands of tokens per weight read, about 4,000 FLOPs per byte here, far above an A100's ~156. Single-user decode is about 1 FLOP per byte.

TTFT is 200 ms, then the model streams 100 tokens at a TPOT of 30 ms. What's the end-to-end latency?

  1. 3.17 s
  2. 3.0 s
  3. 0.23 s
  4. 20 s
$0.2 + 0.03 \times (100 - 1) = 3.17$ s. The first token arrives at TTFT, and the remaining 99 each take one TPOT. 3.0 s forgets the TTFT.

What exactly does continuous batching change compared with static batching?

  1. It makes each forward pass compute fewer FLOPs
  2. It pads every request to the same length
  3. It waits longer to collect a bigger batch
  4. It reschedules after every decode step, so finished requests leave and waiting ones join immediately
The model math is unchanged; only the scheduling granularity changes, from whole requests to single iterations. Waiting to collect a batch is dynamic batching.

Interleaving with M5.5: why does speculative decoding usually give a smaller speedup on a heavily loaded server than for a single user?

  1. The draft model's acceptance rate drops when many users are active
  2. Speculative decoding changes the output distribution at large batch sizes
  3. With a big batch the GPU is closer to compute-bound, so verifying extra draft tokens is no longer nearly free
  4. The KV cache can't store draft tokens
Speculation spends spare compute to save memory-bound steps. A large batch already uses that spare compute, so the extra verification work starts to cost real time. The output distribution stays exact either way.

Key takeaways

  • Prefill (whole prompt at once) is compute-bound; decode (one token per step) is memory-bound, with intensity ≈ batch size.
  • Measure TTFT, TPOT/ITL, throughput and tail percentiles (p99). Latency ≈ TTFT + TPOT × (n − 1); cost per million tokens = GPU price per hour ÷ millions of tokens per hour.
  • Continuous batching (Orca) reschedules every step, so slots never wait for the longest request in a batch.
  • Bigger batches trade a little per-token latency for a lot of throughput, until compute or KV memory runs out.
  • Chunked prefill keeps streams smooth when new requests join; prefix caching reuses KV blocks of shared prompts.
