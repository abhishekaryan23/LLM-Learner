Fine-tune → evaluate → optimize

Warm-up · guess before you learn

Two questions to see where you stand.

When should you build the evaluation set for a fine-tuning project?

  1. First, before any training or prompt tweaking
  2. After training, from examples the model gets wrong
  3. Whenever convenient; it doesn't matter
  4. Never: the training loss tells you enough
An eval set built first can't be shaped, even unconsciously, by what your model happens to do well. Building it from the model's failures, or reusing training data, inflates the score.

Your fine-tuned model scores 78% and the baseline 74% on the same 100 questions. What can you conclude?

  1. Fine-tuning clearly helped by 4 points
  2. Not much yet: with 100 questions each accuracy has a 95% CI of roughly ±8 points; you need a paired test or more data
  3. Fine-tuning hurt the model
  4. Accuracy is meaningless for LLMs
For $p \approx 0.76$ and $n = 100$, the standard error is $\sqrt{0.76 \times 0.24 / 100} \approx 0.043$, so the 95% CI is about ±8.4 points. A 4-point gap may be noise. A paired comparison on the same questions is tighter, but may still not settle it.

The project in one paragraph

Take a small open-weight model (roughly 0.5B to 3B parameters, so a free Colab GPU is enough). Choose one task with a checkable answer. Freeze an eval set. Measure a baseline. Fine-tune with LoRA. Measure again, properly. Quantize. Measure accuracy, size and speed. Decide whether you'd ship it, and write down why. Reading and planning from this page takes about 30 minutes; the project itself is a few evenings.

The numbers in the animation are an illustrative run, but the confidence intervals are computed correctly from them; you'll redo that arithmetic below.

The brief, step by step

  1. Pick a narrow task. Outputs you can check automatically (a label, JSON fields, a number, SQL you can execute), at least a few hundred labelled examples (1,000–5,000 is comfortable), and a baseline that isn't already near-perfect. Good first choices: routing tickets to teams, extracting invoice fields into JSON, unit-conversion word problems. Avoid "make it more helpful" for a first project: it's hard to score.
  2. Build the eval set first (M4.7). At least 200 examples, held out, covering every class and difficulty level. Write down the metric and the exact answer-parsing rules. Deduplicate against the training data, including near-duplicates (M4.3). Freeze the file and record its hash. Tune prompts on a separate dev split, never on the eval set.
  3. Baseline. Your honest best without training: the instruct model with zero-shot and few-shot prompts. Record accuracy with a 95% CI. Optionally, record a much larger model as a ceiling.
  4. Fine-tune with SFT (M3.1) and LoRA (M3.7), or QLoRA if memory is tight. Use the same chat template for training and evaluation, compute the loss only on answer tokens, keep a validation split, and stop when validation loss stops improving (P2.4). Reasonable starting points: $r = 16$ on all linear layers, learning rate $10^{-4}$–$2\times10^{-4}$, 1–3 epochs.
  5. Evaluate with proper statistics (M4.6). Same eval set, same decoding (greedy), same parser. Compare models paired, question by question: a paired bootstrap or McNemar's test, reporting the CI of the difference. Then read at least 20 failures and sort them into causes.
  6. Optional: preference tuning (M3.4). Worth it only when answers have shades of quality (tone, format). Build pairs with chosen = good answers and rejected = the model's own bad ones, train with DPO, and check accuracy didn't regress. Ambitious alternative: GRPO with your checker as the verifier (M3.5).
  7. Quantize and measure (M5.1, M5.6). Merge the adapter, then quantize the weights to 8-bit and 4-bit. For each version measure: accuracy (paired against the 16-bit model), size in memory, latency (time to first token, tokens per second at batch size 1) and throughput at the batch size you expect. State the hardware.
  8. Decide and report. Write the decision rule before you see the final numbers, for example: "ship the 4-bit model if the lower end of the 95% CI for its accuracy change is above −3 points". Then apply it, and say what you'd do next.
Explain like I'm 5

You're entering a baking contest with one recipe: lemon cake. Before baking anything, you write down how the judges will score it and hide a few slices of a cake-tasting test in the freezer so you can't cheat (that's the eval set).

You taste a shop-bought lemon cake first (the baseline). Then you practise your recipe (the fine-tune) and run a blind taste test against the shop cake on the same plates (the paired comparison). Finally you shrink it into cupcakes that bake faster (quantization) and check they still taste as good.

Where the analogy breaks: a taste test is one person's opinion, while your eval is hundreds of exact checks, and "tastes about the same" has to become a number with a confidence interval.

The statistics you'll need

For an accuracy $\hat p$ measured on $n$ questions, the standard error is $\mathrm{SE} = \sqrt{\hat p(1-\hat p)/n}$, and an approximate 95% confidence interval is $\hat p \pm 1.96\,\mathrm{SE}$.

To compare two models on the same $n$ questions, only the questions where they disagree matter. Let $b$ = questions only model 1 gets right and $c$ = questions only model 2 gets right. Then the accuracy difference and its standard error are:

$$\hat d = \frac{b - c}{n}, \qquad \mathrm{SE}(\hat d) = \sqrt{\frac{b + c}{n^2} - \frac{(b - c)^2}{n^3}}$$

This paired SE is usually much smaller than treating the two accuracies as independent, because questions both models get right (or both wrong) add no noise to the difference. The starter notebook gets the same intervals by bootstrap: resample the $n$ questions with replacement 10,000 times, recompute the metric each time, and read off the 2.5th and 97.5th percentiles.

Worked example

From the animation: on $n = 200$ tickets the LoRA model gets 150 right; 34 tickets only LoRA gets right, 8 only the base model gets right.

  1. Accuracy: $\hat p = 150/200 = 0.75$; $\mathrm{SE} = \sqrt{0.75 \times 0.25 / 200} \approx 0.0306$
  2. 95% CI: $0.75 \pm 1.96 \times 0.0306 = 0.75 \pm 0.060$, i.e. $[69.0\%,\ 81.0\%]$
  3. Paired difference: $\hat d = (34 - 8)/200 = 0.13$; $\mathrm{SE} = \sqrt{42/200^2 - 26^2/200^3} = \sqrt{0.001050 - 0.0000845} \approx 0.0311$
  4. CI of the gain: $0.13 \pm 1.96 \times 0.0311 = [+6.9,\ +19.1]$ points. It excludes 0, so the gain is real. (Treating the two models as independent would give an SE of about 0.046, half again as wide.)

Rubric

Use this to grade yourself, or swap with a friend.

  • Must: task, metric and answer-parsing rules written down before training.
  • Must: eval set of at least 200 examples, frozen, deduplicated against training data.
  • Must: baseline, fine-tuned and quantized models all scored on the identical set with identical decoding.
  • Must: every accuracy reported with a 95% CI, and every model comparison as a paired difference with its CI.
  • Must: size and latency measured for each model, with hardware and batch size stated; a decision with its reason.
  • Should: error analysis (a confusion matrix plus 20 failures read and categorised), training and validation loss curves, and at least two fine-tuning seeds or a note on run-to-run variance.
  • Stretch: DPO or GRPO on top of SFT; 8-bit vs 4-bit and two quantization methods compared; a short model card listing limitations.
Why this matters in practice: this loop is the day-to-day work of applied LLM teams, and most mistakes are not in the training code. They are a missing or leaky eval set, numbers compared across different prompts or decoding settings, and "improvements" that sit inside the noise. If your write-up survives the rubric above, it's better evidence than many published claims.
Explain it back · in two or three sentences

Why do we build the eval set before training, and why compare models with a paired test on that same set?

Model answer: An eval set fixed in advance can't be tuned to (or leak into) the training process, so its score is an honest estimate of performance on new data. Scoring every model on the same questions lets us look only at the questions where they disagree; that removes the noise from question difficulty, so the paired CI on the difference is much tighter than comparing two independent accuracies.
Review quiz · the whole course

During your LoRA fine-tune, training loss keeps falling but validation loss starts rising after epoch 2. What should you do? (P2.4)

  1. Train for more epochs until validation loss comes back down
  2. Raise the learning rate
  3. Use the epoch-2 checkpoint (early stopping); the model has started to overfit
  4. Evaluate on the training set instead
Falling training loss with rising validation loss is the signature of overfitting. Keep the checkpoint with the best validation loss, and only then touch the frozen eval set.

Which change does not increase the number of trainable LoRA parameters? (M3.7)

  1. Raising the rank $r$ from 16 to 32
  2. Raising the scaling constant $\alpha$ from 16 to 32
  3. Adding adapters to the MLP layers as well as attention
  4. Switching to a model with a larger hidden size
$\alpha$ only scales the update $\frac{\alpha}{r}BA$; the parameter count is $r(d+k)$ per adapted layer, which grows with $r$, with $d$ and $k$, and with the number of adapted layers.

Why does 4-bit weight quantization speed up generation for a single user? (M5.1, M5.6)

  1. 4-bit arithmetic is four times faster on every GPU
  2. It shortens the prompt
  3. It removes attention's quadratic cost
  4. Decoding one token at a time is limited by memory bandwidth, and 4-bit weights mean far fewer bytes to read per token
At batch size 1, each new token requires streaming every weight from memory, so bytes moved, not arithmetic, set the speed. At large batch sizes the gain shrinks as compute becomes the limit.

You discover 15 of your 200 eval tickets have near-duplicates in the training data. What now? (M4.3)

  1. Remove the overlap (from training or eval), re-run, and report the change
  2. Keep them: more overlap means a higher score
  3. Delete the whole eval set and skip evaluation
  4. Nothing; near-duplicates can't affect the score
That's contamination: the model may have memorised those answers, inflating accuracy. Fix the split and say so in the report.

The 4-bit model's accuracy change is −2 points with 95% CI [−6, +2]. Which statement is right? (M4.6)

  1. Quantization has no effect on accuracy
  2. Quantization costs exactly 2 points
  3. No significant drop was detected, but a drop of up to about 6 points is still consistent with the data
  4. The 4-bit model is better
"Not significant" is not "no effect". The interval says what's plausible: anything from a 6-point loss to a 2-point gain. Whether that's acceptable is a product decision.

Key takeaways

  • Pick a narrow, checkable task, and freeze the eval set first.
  • Always have a baseline, and score every model on the identical set with identical decoding.
  • Report CIs, and compare models with paired differences: only disagreements matter.
  • Quantization is a trade: measure accuracy, size and speed together, and decide with a rule written in advance.
