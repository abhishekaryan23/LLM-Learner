Benchmarks

Lesson 2 of Evaluation

Every model launch comes with a table of scores: MMLU, GSM8K, HumanEval, SWE-bench. Each is a benchmark: a fixed test that lets you compare models on one skill. This lesson shows what's inside one, how the main families work, how to compute pass@k properly, and why the same model can get different scores on the “same” test.

By the end you can

  • Say what a benchmark is (dataset + metric + protocol) and why the protocol matters as much as the data.
  • Name the main benchmark families and what each measures: knowledge, maths, code, agentic software work.
  • Compute pass@k with the unbiased estimator, and explain benchmark saturation.

Warm-up · guess before you learn

Take your best guess. Being wrong now helps the right answer stick later.

Two reports give the same model different MMLU scores, several points apart. What's the most likely reason?

  1. One of the reports is lying
  2. MMLU questions are randomly regenerated each time
  3. They used different prompts, numbers of examples or scoring methods
  4. The model's weights change every time it runs
A benchmark score depends on the protocol: the prompt template, the number of few-shot examples, whether the model reasons first, and how its answer is extracted. Change these and the score moves.

A model solves a coding problem in 2 of 10 attempts. If you randomly hand over 5 of those 10 attempts, how likely is it that at least one works?

  1. 20%
  2. 100%
  3. About 78%
  4. 10%
The only failure is picking 5 of the 8 failed attempts: $\binom{8}{5}/\binom{10}{5} = 56/252 \approx 0.22$. So the chance of at least one pass is about $0.78$. That's pass@5.

A benchmark is three things

Perplexity (M4.1) asks how well a model predicts text. A benchmark asks a sharper question: can it do this task? Every benchmark has three parts:

  1. Dataset: fixed inputs with reference answers or tests, e.g. 164 coding problems with unit tests.
  2. Metric: how one output is scored and the scores are combined, e.g. accuracy, exact match on a final number, pass@k, or the percentage of issues resolved.
  3. Protocol: everything else. The prompt template, how many worked examples are shown first (few-shot vs zero-shot), whether the model may reason step by step, the sampling temperature, the answer-extraction rule, and for agents, which tools and how many steps are allowed.

For example, a multiple-choice test can be scored by comparing the probabilities the model gives to the letters A–D, or by letting it write an answer and parsing out a letter. These are two protocols, and they can give different scores for the same model. A score reported without its protocol is only half a number.

The main families

Knowledge and reasoning: MMLU, MMLU-Pro

MMLU (Hendrycks et al., 2021, “Measuring Massive Multitask Language Understanding”) has about 14,000 four-option multiple-choice test questions across 57 subjects, from elementary maths to law and medicine. Random guessing scores 25%. MMLU-Pro (Wang et al., 2024) was built once top models crowded MMLU's ceiling: ten options per question (random = 10%), more reasoning-heavy questions, and noisy items removed.

Maths: GSM8K, MATH

GSM8K (Cobbe et al., 2021) has about 8,500 grade-school word problems, 1,319 of them in the test set. Each needs a few steps of arithmetic, and the metric is exact match on the final number. MATH (Hendrycks et al., 2021) has 12,500 competition problems (5,000 for testing) across seven subjects and five difficulty levels. Answers are compared after normalising their LaTeX, so $\tfrac{1}{2}$ and $0.5$ can both count.

Code: HumanEval and pass@k

HumanEval (Chen et al., 2021, “Evaluating Large Language Models Trained on Code”) has 164 hand-written Python problems. Each gives a function signature and docstring; the model writes the body, and hidden unit tests decide if it's correct. Code is checked by running it, not by comparing text, which is a big reason code benchmarks are trusted. The metric is pass@k, explained below.

Agentic software work: SWE-bench

SWE-bench (Jimenez et al., 2024) takes 2,294 real GitHub issues from 12 popular Python repositories. The system gets the repository and the issue text and must produce a patch. The task counts as resolved only if the tests that the real fix made pass now pass, and the tests that passed before still pass. This tests navigating a large codebase over many steps, not just writing one function. SWE-bench Verified (OpenAI, 2024) is a 500-task subset that human engineers checked for clear issue descriptions and fair tests. Agent scores also depend on the scaffold, the tools and loop wrapped around the model, so it's part of the protocol.

pass@k: give the model k tries

For code, one sample can fail on a small slip while the next sample works. pass@k is the probability that at least one of k samples passes the tests, averaged over problems. The naive way to measure it is to draw exactly $k$ samples per problem, but that's noisy. Chen et al. instead draw $n \ge k$ samples per problem (they used $n = 200$), count the $c$ that pass, and compute:

$$\text{pass@}k = \mathop{\mathbb{E}}_{\text{problems}}\left[\,1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}\,\right]$$

$\binom{n}{k}$ is the number of ways to choose $k$ of the $n$ samples, and $\binom{n-c}{k}$ is the number of those choices that contain only failures. So the fraction is the chance that a random pick of $k$ is all failures, and one minus it is the chance that the pick contains a pass. If $n - c < k$, every pick must include a pass and pass@k is 1. In code, the binomials get huge, so implementations use the equivalent stable product $1 - \prod_{i=n-c+1}^{n}\left(1 - \frac{k}{i}\right)$.

Worked example

$n = 10$ samples for one problem, $c = 3$ pass.

  1. pass@1 $= 1 - \binom{7}{1}/\binom{10}{1} = 1 - 7/10 = 0.3$, which is simply $c/n$.
  2. pass@2 $= 1 - \binom{7}{2}/\binom{10}{2} = 1 - 21/45 \approx 0.533$.
  3. pass@5 $= 1 - \binom{7}{5}/\binom{10}{5} = 1 - 21/252 \approx 0.917$.
  4. The shortcut $1 - (1 - 0.3)^5 \approx 0.832$ comes out lower. On any one problem the two numbers just differ, but averaged over problems the shortcut is biased low: because $1 - (1-p)^k$ is concave in $p$, plugging in a noisy estimate of $p$ underestimates pass@k on average (Jensen's inequality).

Explain like I'm 5

Three little robots run the same obstacle course, and the kids in the stands compare them. That's a benchmark.

It's only fair if everything is the same: the same obstacles (the questions), the same stopwatch (the score), and the same rules, like where you start and whether you may try a jump twice (the protocol). If one robot gets two tries at every jump, its time isn't comparable.

And once every robot zooms round the course perfectly, the kids can't tell them apart any more. Time to build a harder course!

Where it breaks: a robot can be great at this one course and clumsy everywhere else. A benchmark measures one slice of skill, not the whole robot.

Saturation: why new benchmarks keep appearing

Benchmarks follow a life cycle. A new one is hard, models climb it, and eventually the top scores bunch up near the ceiling. Then it is saturated: the remaining gaps are within noise, and the ceiling itself is below 100% because some questions have wrong or ambiguous labels. A re-annotation of MMLU (Gema et al., 2024, “Are We Done with MMLU?”) estimated errors in a few percent of questions overall, and far more in some subjects.

The pace is fast. The GPT-4 technical report (OpenAI, 2023) already reported 86.4% on MMLU, five-shot. When SWE-bench appeared, the best model in the paper resolved under 2% of issues; within about two years, leading agent systems were resolving well over half of SWE-bench Verified, and by 2026 third-party leaderboards reported top scores above 90%. Audits suggesting some solutions were memorized mean part of that may be contamination (M4.3), but either way Verified is now close to saturated. So the field keeps moving to harder or fresher tests: MMLU to MMLU-Pro and GPQA, GSM8K to MATH and competition problems, HumanEval to contamination-resistant sets like LiveCodeBench and to SWE-bench. Contamination (M4.3) speeds up saturation too: once test questions leak into training data, high scores stop meaning much.

Small protocol changes, big swings

LLMs can be surprisingly sensitive to details that shouldn't matter:

  • Format: Sclar et al. (2023) varied only the prompt formatting (separators, casing, spacing) and found few-shot accuracy differences of up to 76 points on some tasks for an open 13B model. The sensitivity persisted in larger and instruction-tuned models too, though the typical (median) spread across tasks was smaller, about 7.5 points.
  • Few-shot examples: which examples you show, and in what order, can move results (Zhao et al., 2021, “Calibrate Before Use”).
  • Scoring: letter-probability vs generate-and-parse, strict vs lenient answer extraction, with or without step-by-step reasoning.

The defences are to use a shared, public harness (for example EleutherAI's lm-evaluation-harness or Stanford's HELM, Liang et al., 2022), publish the exact prompts, report the number of shots and the sampling settings, and where possible average over several prompt variants and report the spread. How to put proper error bars on a score is the topic of M4.6.

Why this matters in practice: when you read a model card, check the fine print before comparing numbers. Was it 0-shot or 5-shot? With or without chain-of-thought? pass@1 or pass@10? The full SWE-bench or Verified, and with which scaffold? Public benchmarks are a good first filter for choosing a model, but they rarely look like your task. For that you build your own evals (M4.7).
Explain it back · in two or three sentences

Explain what pass@k measures and why Chen et al. compute it from $n > k$ samples with the binomial formula rather than just drawing $k$ samples.

Model answer: pass@k is the probability that at least one of k sampled solutions passes the unit tests, averaged over problems. Drawing exactly k samples per problem gives a very noisy estimate. Drawing n ≥ k samples, counting the c that pass, and computing $1 - \binom{n-c}{k}/\binom{n}{k}$ uses all the samples and is unbiased, while the shortcut $1-(1-c/n)^k$ underestimates on average.
Check yourself

To measure pass@10, why sample with temperature above 0 instead of greedy decoding?

  1. Greedy decoding is too slow for code
  2. Greedy decoding returns the same completion every time, so 10 “tries” are really one
  3. Temperature makes each individual sample more accurate
  4. The unit tests require random outputs
Greedy decoding always picks the most likely token (M1.5), so repeated runs are identical. pass@k only makes sense with diverse samples. Teams often report pass@1 at low temperature and pass@k at a higher one.

$n = 5$ samples, $c = 1$ passes. What is the unbiased estimate of pass@5?

  1. 0.2
  2. 0.67
  3. 1
  4. 0.5
Picking all 5 samples always includes the passing one: $\binom{4}{5} = 0$, so pass@5 $= 1$. The shortcut $1 - 0.8^5 \approx 0.67$ would underestimate.

What does it mean that a benchmark is “saturated”?

  1. Top models score near the ceiling, so differences between them are within noise and label errors
  2. The benchmark has too many questions to run cheaply
  3. Every model scores exactly 100%
  4. The benchmark only contains multiple-choice questions
Near the ceiling, a benchmark can no longer separate strong models, and label noise caps the top score below 100%. That's when harder or fresher replacements appear.

Lab A reports “HumanEval 92%” and lab B reports “HumanEval 86%” for their models. What should you check before concluding A is better?

  1. Nothing; both are HumanEval
  2. Which lab has the larger model
  3. Whether the scores were published in the same month
  4. That both are the same metric (e.g. pass@1) under the same prompting and sampling protocol, and whether the gap exceeds the noise on 164 problems
Protocol (pass@1 vs pass@10, prompt, temperature) can easily move scores by more than 6 points. And with only 164 problems, one problem is worth about 0.6 points, so small gaps may be noise (M4.6).

Key takeaways

  • A benchmark is dataset + metric + protocol. Change the protocol and the score changes.
  • Families: knowledge (MMLU, MMLU-Pro), maths (GSM8K, MATH), code (HumanEval, pass@k), agentic software work (SWE-bench).
  • Unbiased pass@k: draw $n$ samples, count $c$ passing, compute $1 - \binom{n-c}{k}/\binom{n}{k}$ and average over problems.
  • Benchmarks saturate, and contamination speeds that up, so new, harder ones keep appearing.
  • Formatting and few-shot choices can swing scores; use a fixed public harness and report the protocol.
