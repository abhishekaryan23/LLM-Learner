Distributed training & mixed precision

Lesson 5 of Pretraining

A 7B model doesn't fit in one GPU's memory for training, and even if it did, pretraining it on one GPU would take years. This lesson shows how the work is split across thousands of GPUs, and how lower-precision numbers make every GPU go further.

By the end you can

  • Account for the ~16 bytes per parameter of mixed-precision AdamW training, and compute it for a 7B model.
  • Explain data, ZeRO/FSDP, tensor and pipeline parallelism, including the pipeline bubble.
  • Compare fp32, fp16 and bf16, and explain loss scaling and activation checkpointing.
Before you start: this lesson leans on Adam's two moment estimates from M2.3 Optimizers and on $C \approx 6ND$ from M2.4 Scaling laws. Knowing what backpropagation stores (P2.3) helps with the activations part.

Why one GPU isn't enough

Memory. Mixed-precision training with AdamW keeps, for every parameter (Rajbhandari et al., 2020):

  • bf16 (or fp16) weights for the forward and backward pass: 2 bytes
  • bf16 gradients: 2 bytes
  • an fp32 master copy of the weights, which the optimizer updates: 4 bytes
  • Adam's first and second moments $m$ and $v$ in fp32 (M2.3): 4 + 4 bytes

That's $2 + 2 + 4 + 4 + 4 = 16$ bytes per parameter. For 7B parameters: $7\times10^9 \times 16 = 1.12\times10^{11}$ bytes, 112 GB, against 80 GB on an H100. And that's before activations, the intermediate values saved for the backward pass, which grow with batch size, sequence length and depth.

Compute. Pretraining a 7B model on 2T tokens takes $6ND = 6 \times 7\times10^9 \times 2\times10^{12} = 8.4\times10^{22}$ FLOPs. At a realistic $4\times10^{14}$ FLOP/s on one H100, that's $2.1\times10^{8}$ seconds: about 6.7 years. We need many GPUs, and ways to split both the memory and the work.

Data parallelism, then sharding (ZeRO / FSDP)

Data parallelism (DP) is the simplest split: every GPU holds the whole model, processes a different slice of the batch, and then the GPUs all-reduce (sum and share) their gradients so everyone applies the same update. It divides the compute, but every GPU still needs all 16 bytes per parameter.

ZeRO (Rajbhandari et al., 2020) removes that redundancy by giving each of the $N_d$ data-parallel GPUs only a shard of the training state. With $\Psi$ parameters, per-GPU memory is:

  • Stage 1, shard the 12 bytes of optimizer state: $4\Psi + 12\Psi/N_d$
  • Stage 2, also shard gradients: $2\Psi + 14\Psi/N_d$
  • Stage 3, also shard the weights: $16\Psi/N_d$. Each layer's weights are gathered from the other GPUs just before use and dropped afterwards. PyTorch's FSDP (Fully Sharded Data Parallel) works the same way.

The price is communication: stage 3 moves about 1.5× as much data as plain DP, so fast interconnects matter.

Tensor parallelism: split each layer

Sharding stores the weights in pieces, but each GPU still computes whole layers. Tensor parallelism (Megatron-LM, Shoeybi et al., 2019) splits the matrix multiplications themselves. In the MLP, the first weight matrix is split by columns, so each GPU computes its own slice of the hidden units; the second is split by rows, and one all-reduce adds the partial results:

$$Y = \big[\,X A_1 \;\big|\; X A_2\,\big], \qquad Z = Y_1 B_1 + Y_2 B_2$$

Here $A = [A_1 \mid A_2]$ is the first weight matrix split between two GPUs and $B$ the second, split the other way; attention is split by heads in the same spirit. This needs communication inside every layer, so tensor parallelism usually stays within one server, whose 8 GPUs are linked by very fast NVLink.

Pipeline parallelism: split the stack of layers

Pipeline parallelism puts consecutive groups of layers on different GPUs, like an assembly line. Its problem is idle time: the last stage waits for the first to finish, and vice versa on the way back. GPipe (Huang et al., 2019) splits each batch into $m$ micro-batches to keep the line busy. With $p$ stages, the idle fraction (the bubble) is

$$\text{bubble} = \frac{p-1}{m+p-1}$$

Schedules such as 1F1B (one forward, one backward; Narayanan et al., 2019) interleave the passes so fewer micro-batches' activations are held at once, and interleaved stages shrink the bubble further.

Big runs combine all of these, often called 3D parallelism. Llama 3 405B was trained on up to 16,384 H100 GPUs: 8-way tensor parallelism inside each server, 16-way pipeline parallelism, and 128-way data parallelism with FSDP-style sharding, plus context parallelism for long sequences. Meta reported keeping roughly 38–43% of the GPUs' peak throughput busy with useful work.

Explain like I'm 5

One chef can't make a pizza the size of a room: it won't fit on their table, and it would take forever. So many chefs at separate tables each make one part of it.

Then all the parts are carried to one big board and fitted together. The chefs have to keep talking ("my slice ends here!") so the pieces match up. That talking is the communication between GPUs.

Where it breaks: GPUs don't only split one pizza into pieces. Sometimes they each bake a whole pizza from different dough and then agree on one recipe change (data parallelism), or pass the pizza down a line where each chef adds one topping (pipeline parallelism).

Mixed precision: fp32, fp16 and bf16

A floating-point number has a sign, an exponent (which sets its range) and a mantissa (which sets its precision). Modern GPUs run 16-bit matrix maths many times faster than 32-bit and halve the memory, so training does the heavy work in 16 bits:

  • fp16 can't represent anything above 65,504, and its smallest positive value is about $6\times10^{-8}$, so smaller gradients underflow to zero. The fix is loss scaling (Micikevicius et al., 2018): multiply the loss by a large factor $S$ (e.g. $2^{16}$) so all gradients are scaled up into range, divide them by $S$ in fp32 before the update, and lower $S$ (skipping that step) if any gradient overflows to infinity.
  • bf16 has fp32's range, so loss scaling is usually unnecessary. It's the default for LLM training on modern hardware.
  • Either way, an fp32 master copy of the weights receives the updates. Updates are often thousands of times smaller than the weights, and 16-bit numbers can't register such small changes.
  • Since 2024 some labs go further with FP8 matrix multiplications, for example DeepSeek-V3, with careful scaling to manage FP8's tiny range and precision.

Worked example: a lost update

Numbers between 1 and 2 in bf16 are spaced $2^{-7} = 0.0078125$ apart (7 mantissa bits).

  1. A weight equals 1.0 and the optimizer's update is $+0.001$.
  2. The exact result 1.001 lies between 1.0 and the next bf16 number, 1.0078125.
  3. It's much closer to 1.0, so it rounds to 1.0: the update vanished.
  4. Repeat that for thousands of steps and the weight never moves. In the fp32 master copy (spacing about $1.2\times10^{-7}$ near 1), the update survives, and the bf16 copy is re-made from it each step.

Activation checkpointing

Backpropagation (P2.3) needs the activations from the forward pass, and for long sequences they can take more memory than the weights. Activation checkpointing (Chen et al., 2016) keeps only some of them, typically each layer's input, and recomputes the rest during the backward pass. Full recomputation costs about one extra forward pass, roughly $2N$ more FLOPs per token on top of $6N$, about 33% more compute, in exchange for a large cut in activation memory. Selective recomputation (Korthikanti et al., 2022) recomputes only the cheap-to-redo but memory-hungry parts, such as attention scores, for a much smaller overhead.

Why this matters in practice: choosing a parallelism layout is a juggling act between memory, communication and idle time, and it decides how much of a cluster's theoretical speed you actually get (model FLOPs utilization, often 30–50% for large runs). The same 16-bytes-per-parameter arithmetic explains why fine-tuning tricks like LoRA and QLoRA (M3.7) are so popular, and why inference uses quantization (M5.1): with no gradients or optimizer state, a model can be served in a fraction of its training memory.
Explain it back · in two or three sentences

Why doesn't plain data parallelism solve the memory problem, and what does ZeRO-3 / FSDP do differently?

Model answer: In data parallelism every GPU keeps a full copy of the weights, gradients and optimizer state (about 16 bytes per parameter), so adding GPUs speeds training up but doesn't reduce per-GPU memory. ZeRO-3 / FSDP shards all of that across the GPUs so each stores only $1/N_d$ of it, gathering each layer's weights just in time for its computation, at the cost of more communication.
Check yourself

With ZeRO stage 3 on 8 GPUs, how much memory per GPU does a 7B model's training state (16 bytes/parameter) take?

  1. 112 GB
  2. 14 GB
  3. 38.5 GB
  4. 7 GB
$16 \times 7\text{B} / 8 = 14$ GB. 38.5 GB would be ZeRO-1 on 8 GPUs: $4\Psi + 12\Psi/8 = 28 + 10.5$.

A pipeline has 8 stages and you use 8 micro-batches. What fraction of time is lost to the bubble?

  1. 0%
  2. 12.5%
  3. 87.5%
  4. About 47%
$(p-1)/(m+p-1) = 7/15 \approx 47\%$. You need many more micro-batches than stages to make the bubble small.

Linking back to M2.3: which part of the 16 bytes per parameter exists because of the optimizer, and how big is it?

  1. Adam's $m$ and $v$ plus the fp32 master weights: 12 bytes
  2. The bf16 gradients: 2 bytes
  3. The bf16 weights: 2 bytes
  4. Nothing; Adam needs no extra memory
Adam keeps two fp32 running averages per parameter (8 bytes), and the fp32 master copy it updates adds 4 more. That 12-byte block is exactly what ZeRO stage 1 shards.

Why does fp16 training need loss scaling while bf16 training usually doesn't?

  1. fp16 is less precise than bf16
  2. bf16 uses 32 bits
  3. fp16 has only 5 exponent bits, so small gradients underflow to zero unless scaled up; bf16 has fp32's 8 exponent bits
  4. Loss scaling is only for inference
It's about range, not precision. fp16 is actually more precise than bf16, but its smallest values are far larger than fp32's or bf16's.

Key takeaways

  • Mixed-precision AdamW needs about 16 bytes per parameter (7B → 112 GB) plus activations: more than one GPU holds.
  • Data parallelism splits the batch; ZeRO/FSDP shards optimizer state, gradients and weights across those GPUs.
  • Tensor parallelism splits matrices inside a layer (within a server); pipeline parallelism splits the layers, with bubble $(p-1)/(m+p-1)$.
  • bf16 has fp32's range with less precision; fp16 needs loss scaling; fp32 master weights keep small updates from vanishing.
  • Activation checkpointing trades about a third more compute for much less activation memory.
