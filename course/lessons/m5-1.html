Quantization

Lesson 1 of Optimization

A 70-billion-parameter model in 16-bit needs 140 GB just for its weights: two big GPUs before it says a word. Store each weight in 4 bits instead and it fits on one, and it generates text faster too. This lesson shows how you squeeze numbers into so few bits, and what it costs.

By the end you can

  • Work out a model's weight memory in fp32, bf16, int8 and int4, and explain why fewer bytes also means faster decoding.
  • Quantize and dequantize numbers by hand with a scale and a zero-point.
  • Explain why outliers hurt, and how per-channel and group-wise scales, LLM.int8(), GPTQ, AWQ and quantization-aware training respond to them.

A 70-billion-parameter model stored in bf16 needs roughly how much memory just for its weights?

  1. 35 GB
  2. 70 GB
  3. 140 GB
  4. 280 GB
bf16 uses 2 bytes per parameter, so $70 \times 10^9 \times 2$ bytes $= 140$ GB. In int4 (half a byte each) it would be about 35 GB.

When a model generates one token at a time for a single user, the GPU must read every weight from memory for each token. If you halve the bytes per weight, you mostly…

  1. save memory but gain no speed
  2. roughly double the ceiling on tokens per second, because reading weights is the bottleneck
  3. make generation slower, because the weights must be unpacked
  4. speed up training, but not generation
Single-stream decoding is limited by memory bandwidth, not arithmetic. Fewer bytes to read means more tokens per second, even though the GPU unpacks the weights before multiplying.

Why: memory and bandwidth

Every parameter is a number, and the format decides how many bytes it takes:

FormatBytes / param7B model70B model
fp32428 GB280 GB
bf16 / fp16214 GB140 GB
int8 / fp817 GB70 GB
int40.53.5 GB35 GB

GB here means $10^9$ bytes. Real 4-bit formats add a little for their scales (about 4.1 to 4.9 bits per weight: NF4 ≈ 4.1, MXFP4 4.25, llama.cpp's Q4_0 4.5 and Q4_K_M ≈ 4.8 to 4.9), and serving also needs room for the KV cache and activations.

So a 70B model in bf16 needs two 80 GB GPUs just to hold the weights, while in int4 it fits on one with room to spare. That's the memory win.

The speed win is less obvious. When a model generates text for one user, each new token needs one pass through the network, and every weight must be read from GPU memory once. The arithmetic per weight is tiny, so the GPU spends most of its time waiting for bytes. An H100 SXM reads about 3.35 TB/s from its memory, which gives a ceiling of:

$$\text{tokens/s} \;\lesssim\; \frac{\text{memory bandwidth}}{\text{bytes of weights}} = \frac{3.35\ \text{TB/s}}{14\ \text{GB}} \approx 240 \quad(\text{7B in bf16})$$

In int4 the weights are 3.5 GB, so the ceiling rises to about 960 tokens/s. Real systems reach only part of this, but the ratio holds: fewer bytes per weight means proportionally faster single-stream decoding. With large batches the GPU becomes busy with arithmetic instead, which is where 8-bit compute formats help (more in M5.6).

Uniform affine quantization

The basic recipe maps a range of real numbers onto a small set of evenly spaced integer codes. With $b$ bits there are $2^b$ codes: 16 for 4-bit, 256 for 8-bit.

$$q = \mathrm{clamp}\!\left(\mathrm{round}\!\left(\frac{x}{s}\right) + z,\; q_{\min},\; q_{\max}\right) \qquad\qquad \hat{x} = s\,(q - z)$$
  • $x$ is the real number (a weight) and $q$ the integer code we store.
  • $s$ is the scale: the gap between neighbouring levels, in real units.
  • $z$ is the zero-point: the code that stands for exactly $0.0$.
  • $\hat{x}$ ("x-hat") is the dequantized value used in the computation. $x - \hat{x}$ is the rounding error, at most $s/2$ inside the range.

For the asymmetric (affine) version with codes $0 \ldots 2^b - 1$, fit the grid to the data: $s = \dfrac{x_{\max} - x_{\min}}{2^b - 1}$ and $z = -\mathrm{round}(x_{\min}/s)$. The symmetric version sets $z = 0$ and $s = \max|x| / (2^{b-1} - 1)$, using codes $-127 \ldots 127$ for int8. It wastes a little range when the data is lopsided, but it's simpler and faster, so it's the usual choice for weights, which are roughly centred on zero.

Explain like I'm 5

The giant crayon box has hundreds of colours: three slightly different blues, five greens. The small box has only a few.

If you draw the same picture with the small box, you pick the closest crayon for every colour. Up close it's a tiny bit different, but from across the room it looks nearly the same, and the small box fits in your pocket.

Where the analogy breaks: a model doesn't just look at the picture. Its tiny colour errors add up through dozens of layers, so a few weights need extra care.

Worked example

Quantize $x = [-1.20,\ -0.35,\ 0.00,\ 0.47,\ 1.80]$ to asymmetric 4-bit (codes 0 to 15).

  1. Scale: $s = (1.80 - (-1.20)) / 15 = 3.00 / 15 = 0.20$.
  2. Zero-point: $z = -\mathrm{round}(-1.20 / 0.20) = -(-6) = 6$.
  3. Codes: $x/s = [-6,\ -1.75,\ 0,\ 2.35,\ 9]$. Round and add 6: $q = [0,\ 4,\ 6,\ 8,\ 15]$.
  4. Dequantize: $\hat{x} = 0.2\,(q - 6) = [-1.20,\ -0.40,\ 0.00,\ 0.40,\ 1.80]$.
  5. Errors: $0,\ 0.05,\ 0,\ 0.07,\ 0$, all below $s/2 = 0.10$. Zero came back exactly, which matters: zeros from padding or ReLU-style activations stay zero.

How many numbers share a scale?

Every scale is a compromise for all the numbers that share it: one big value forces a coarse grid on everyone else. So the main design choice is the granularity:

  • Per-tensor: one scale for the whole weight matrix. Cheapest, but the largest weight anywhere sets the grid for millions of others.
  • Per-channel: one scale per output row of the matrix. Rows can differ a lot in size, so this is much better and still nearly free. It's the standard for int8 weights.
  • Group-wise: one scale (and maybe a zero-point) per block of, say, 32, 64 or 128 consecutive weights. This is what makes 4-bit work. The cost is storage: an fp16 scale per 128 weights adds $16/128 = 0.125$ bits per weight, so "4-bit" is really about 4.125 bits.

Not every format is integer. FP8 (E4M3 and E5M2) is a tiny floating-point number, so its levels are dense near zero and sparse far out, a good match for bell-shaped data. QLoRA's NF4 places its 16 levels at the quantiles of a normal distribution. And recent NVIDIA GPUs (Blackwell) run 4-bit floating-point formats in hardware, MXFP4 and NVFP4, which share one scale per block of 32 or 16 values. OpenAI's gpt-oss models (2025), for example, shipped with their expert weights in MXFP4.

The outlier problem

Weights are mostly well behaved. Activations, the numbers flowing between layers, are not. Dettmers et al. (2022, "LLM.int8()") found that in transformers from about 6.7B parameters up, a handful of hidden dimensions carry values up to around 20 times larger than the rest, in almost every layer and token. Quantize those activations to int8 with a shared scale and the ordinary values collapse to a few codes; quality falls apart.

Their fix, LLM.int8(), splits each matrix multiplication in two. The few feature dimensions that contain outliers (magnitude above a threshold of 6) are multiplied in fp16; everything else uses int8 with a separate scale per row and column. More than 99.9% of the values still go through int8, and quality matched the 16-bit model up to 175B parameters. A related trick, SmoothQuant (Xiao et al., 2023), divides the troublesome activation channels by a per-channel factor and multiplies the matching weights by the same factor. The product is unchanged, but the outliers move into the weights, which tolerate them better. That makes 8-bit weights and activations (W8A8) practical.

Weight-only post-training quantization: GPTQ and AWQ

Post-training quantization (PTQ) compresses a finished model with no further training, using at most a small calibration set of a few hundred text samples. The simplest PTQ is round-to-nearest (RTN), exactly what the animation did. RTN works well at 8 bits but loses noticeably at 4 bits and below. Two widely used methods do better while keeping the "W4A16" setup: 4-bit weights, 16-bit activations, and weights unpacked to 16-bit inside the matmul kernel.

  • GPTQ (Frantar et al., 2023) quantizes a layer one column at a time. After rounding each column, it adjusts the weights not yet quantized so the layer's output on the calibration data, $\lVert WX - \hat{W}X \rVert^2$, changes as little as possible. It uses second-order information (the matrix $XX^\top$) to decide how. The authors quantized 175B-parameter models to 3–4 bits in about four GPU hours, with small accuracy loss.
  • AWQ (Lin et al., 2024, "Activation-aware Weight Quantization") starts from the observation that a small fraction of weights, roughly 1%, matter far more than the rest, and that you find them by looking at the activations they multiply, not the weights themselves. Instead of keeping those in 16-bit, AWQ scales up the important input channels before quantizing (and scales the activations down to match), so their relative rounding error shrinks. There's no backpropagation and no weight reconstruction, so it's fast and generalizes well.

In practice you'll meet these as file formats and flags: GPTQ and AWQ checkpoints in serving engines such as vLLM, FP8 checkpoints on H100-class GPUs, and llama.cpp's GGUF "k-quants" (Q4_K_M and friends) on laptops.

Why this matters in practice: quantization is usually the first optimization anyone applies to a deployed LLM. A 4-bit 70B model fits on one 80 GB GPU instead of two, an 8B model runs on a laptop, and single-user generation speeds up roughly in proportion to the bytes saved. QLoRA (M3.7) uses the same idea for fine-tuning: a frozen 4-bit NF4 base plus small 16-bit adapters.

Quantization-aware training

PTQ asks a model trained in high precision to cope with rounding it never saw. Quantization-aware training (QAT) lets the model adapt: during training (or a short fine-tune), the forward pass rounds the weights to the target grid ("fake quantization"), so the loss reflects the quantized model.

There's a catch. $\mathrm{round}(\cdot)$ is a staircase: its derivative is zero almost everywhere, so backpropagation would get no signal. The standard fix is the straight-through estimator (STE): in the backward pass, pretend the rounding was the identity and let the gradient pass through unchanged. QAT costs extra training compute, but it gives the best quality at very low bit-widths. Google, for example, released QAT-trained int4 versions of Gemma 3 in 2025.

Quantizing the KV cache

Weights aren't the only big tensor. The KV cache (M1.5) stores a key and a value vector per token, per layer. For a 7B model with 32 layers and 4,096-dimensional keys and values in fp16, that's $2 \times 32 \times 4096 \times 2$ bytes $= 0.5$ MiB per token, or 2 GiB for a single 4,096-token conversation. Long contexts and big batches multiply that, so the cache often limits how many users fit on a GPU.

Storing the cache in FP8 or int8 halves it; 4-bit or even 2-bit caches have been shown to work with careful grouping. Keys tend to have outlier channels, so methods such as KIVI (Liu et al., 2024) quantize keys per channel and values per token. Paged attention (M5.4) manages the same cache from the allocation side.

Measuring the quality loss

Never assume a quantized model is "the same model". Check it:

  1. Perplexity on held-out text (M4.1): cheap, and a good first alarm. But a small rise can hide large damage on specific skills.
  2. KL divergence between the original and quantized model's next-token distributions on the same text: it measures directly how much the predictions moved (llama.cpp's tools report it).
  3. Task benchmarks (M4.2), including the hard ones: math, code, long-context retrieval and non-English text are often reported to degrade first.
  4. Your own evals on your own prompts, since that's the traffic that matters.

Rough rules of thumb, which vary by model and method: 8-bit weights (int8 or FP8) are usually close to lossless; good 4-bit weight-only methods typically cost a little; 3 bits and below degrade clearly, and smaller models suffer more than large ones.

Explain it back · in two or three sentences

With W4A16, the GPU unpacks 4-bit weights back to 16-bit before multiplying. So why does single-user generation still get faster?

Model answer: Generating one token for one user needs very little arithmetic per weight, so the GPU is limited by how fast it can read weights from memory, not by the math. 4-bit weights are a quarter of the bytes of bf16, so each token needs a quarter of the memory traffic; unpacking happens in fast on-chip registers and costs comparatively little.
Check yourself

You quantize a weight matrix to symmetric int8 with one scale for the whole tensor. One weight is 40× larger than every other weight. What happens?

  1. Nothing much: int8 has 255 levels, plenty for everyone
  2. The scale grows about 40×, so the ordinary weights are squeezed into a few codes near zero and lose most of their precision
  3. The outlier is clipped to the largest code, and everything else is exact
  4. The quantizer automatically switches that weight to fp16
The scale is set by $\max|w|$, so the big weight stretches the grid for everyone. The ordinary weights then span only about 3 of the 127 positive codes. Per-channel or group-wise scales, or keeping outliers in 16-bit (LLM.int8()), are the fixes. Nothing switches formats automatically.

A model uses 4-bit weights with group size 128 and one fp16 scale per group (no zero-point). How many bits per weight does it really store?

  1. 4.0
  2. 4.125
  3. 4.5
  4. 5.0
Each group of 128 weights carries one 16-bit scale: $16/128 = 0.125$ extra bits, so 4.125 bits per weight. Adding a 16-bit zero-point per group too would make it 4.25.

What is the key idea of AWQ?

  1. Fine-tune the whole model with quantization in the loop
  2. Keep the largest-magnitude weights in fp16
  3. Quantize activations to 4 bits along with the weights
  4. Find the important weight channels from activation magnitudes and scale them up before quantizing, so their relative error shrinks
AWQ is post-training and activation-aware: importance comes from the activations a weight multiplies, and protection comes from per-channel scaling rather than mixed precision. Fine-tuning with quantization in the loop is QAT.

In quantization-aware training the forward pass rounds the weights. Why can't plain backpropagation (P2.3) train through that rounding without help?

  1. Rounding is a staircase whose derivative is 0 almost everywhere, so no gradient would reach the weights; the straight-through estimator treats it as the identity in the backward pass
  2. Rounding is too expensive to compute on GPUs
  3. Integers cannot be stored in a computation graph
  4. The learning rate would have to be exactly zero
Gradient descent needs a useful slope. A step function is flat between jumps, so the chain rule multiplies by zero. The STE passes the incoming gradient straight through, which works well in practice.

Key takeaways

  • Bytes per parameter: fp32 4, bf16 2, int8/fp8 1, int4 0.5. A 70B model is 140 GB in bf16 and about 35 GB in int4.
  • Single-stream decoding is bandwidth-bound, so fewer bytes per weight means faster generation, not just less memory.
  • Quantize: $q = \mathrm{round}(x/s) + z$. Dequantize: $\hat{x} = s(q - z)$. The error is at most $s/2$.
  • Outliers stretch the scale. Finer granularity (per-channel, group-wise), mixed precision (LLM.int8()) and smarter PTQ (GPTQ, AWQ) fight them; QAT lets the model adapt.
  • Always measure: perplexity, KL to the original, hard benchmarks and your own evals.
