AGENTS.md & project memory files

Lesson 5 of The agent toolkit

Every agent session starts with a blank memory. A rules file is a short note you write once, which the agent reads at the start of every session: how to build, how to test, what never to touch. It is the cheapest, highest-value thing you can add to a repo that agents work in.

By the end you can

  • Explain what a rules file (AGENTS.md, CLAUDE.md and friends) is, when it loads and which file wins when several apply.
  • Write a short, specific rules file: real commands, conventions, gotchas, boundaries, and no secrets.
  • Choose between a rules file, an Agent Skill and a memory file for a given piece of knowledge.
Builds on: Context engineering (AG.2): everything the agent knows this turn has to fit in one context window, so every line you add competes with everything else. Helpful but optional: Agent Skills (AG.4), which this lesson compares rules files against.
Warm-up · guess before you learn

Take your best guess. A wrong guess now makes the right answer stick later.

Your coding agent keeps running npm test, but your project uses pnpm test:unit. What is the cheapest fix that lasts?

  1. Fine-tune the model on your repo
  2. Switch to a bigger model
  3. Write the right command once in a rules file at the root of the repo
  4. Remind it in every chat message
A rules file is read at the start of every session, so one line fixes it for everyone on the team and every future session. Fine-tuning is far too heavy for a fact that fits in one line.

Which line belongs in a rules file that is committed to the repo?

  1. The API key for the staging server
  2. "Run make check before you finish; it must pass."
  3. The full 40-page architecture document, pasted in
  4. "Write clean, high-quality code."
A good rule is short, specific and checkable. Secrets never go in (the file is shared and pasted into the model's context), long docs belong behind a link, and vague advice changes nothing.

A README for agents

A coding agent is a model in a loop that reads files, runs commands and edits code (SY.5). Each new session starts from zero. It doesn't know that your project uses pnpm, that tests need Docker running, or that the migrations/ folder is generated and must never be edited by hand. So it guesses, and you correct it, again and again.

From 2024 on, each coding tool solved this with its own instructions file: .cursorrules for Cursor, CLAUDE.md for Claude Code, .github/copilot-instructions.md for GitHub Copilot, GEMINI.md for Gemini CLI. A repo used by several tools ended up with several copies of the same advice. In August 2025 a group of tool makers (OpenAI Codex, Amp, Google's Jules, Cursor and Factory) settled on one shared name: AGENTS.md. In December 2025 OpenAI donated it to the new Agentic AI Foundation under the Linux Foundation, alongside Anthropic's MCP and Block's goose. Its site says it is used by over 60,000 open-source projects.

The idea is simple. The format's own description: "Think of AGENTS.md as a README for agents: a dedicated, predictable place to provide context and instructions to help AI coding agents work on your project." Your README is for humans: what the project is and how to get started. AGENTS.md holds the extra detail an agent needs:

  • Setup: how to install and run the project.
  • Test: the exact commands that must pass before the work is done.
  • Code style: conventions a linter can't enforce.
  • Gotchas: the traps a newcomer falls into.
  • PR rules: how commits and pull requests should look.
  • Don't touch: generated, vendored or protected files.

It is plain Markdown with no required fields: use whatever headings help. The agent reads the whole file into its context window at the start of the session. That is its strength (it is always there) and its cost: every line is paid for in tokens, in every session, and competes with everything else for the model's attention (AG.2).

Explain like I'm 5

A new helper robot arrives at a woodworking workshop. Before it touches anything, it reads one welcome poster pinned by the door: where the tools live, "always wear goggles", "sweep up before you leave", "never touch the big saw".

The owner doesn't have to repeat the rules every morning. Any new helper, from any robot company, reads the same poster and knows how this workshop works.

The poster is AGENTS.md. Keeping it to one short poster matters: a 40-page rulebook by the door would never get read properly.

Where it breaks: a robot reads the whole poster every single time it walks in, and the poster takes up room in its small "working memory". A real helper would remember it after day one.

Why does AGENTS.md exist as a separate file instead of putting everything in the README?

  1. Agents can't read README files
  2. AGENTS.md is a strict schema with required fields
  3. It is encrypted so humans can't see it
  4. It gives agents one predictable place for build, test and convention details, while the README stays short for humans
Agents can read READMEs, and AGENTS.md has no required fields. The point is a predictable, agent-focused file, so every tool knows where to look and the README stays readable for people.

Which file loads, and which one wins

Real repos have more than one rules file. A monorepo might have a root AGENTS.md with team-wide rules plus a nested one inside each package. The AGENTS.md convention is short: the closest AGENTS.md to the file being edited wins, and explicit instructions in the chat override everything. Watch it happen:

In practice, tools usually combine the files rather than throw the root one away: the root rules still apply, and the nearer file only wins where the two disagree. The details differ by tool. Claude Code, for example, concatenates every CLAUDE.md from the root down to where you launched it (closer files are read last) and loads files in subfolders only when it works there. So keep each file self-consistent and avoid contradicting the root unless you mean to.

Most tools also have their own file names. As of late 2026 most of them also read AGENTS.md, but check each tool's docs, because this changes quickly:

One source of truth. If your team uses several tools, keep the real rules in AGENTS.md and make each tool-specific file point at it: a one-line CLAUDE.md containing @AGENTS.md, a symlink, or a setting. Two copies of the same rules always drift apart.

The root AGENTS.md says "use 4-space indents"; packages/web/AGENTS.md says "use 2-space indents". The agent edits packages/web/app.ts. What should it use, if you said nothing in the chat?

  1. 2 spaces: the closest file wins where they conflict
  2. 4 spaces: the root file always wins
  3. Whichever file it happened to read first
  4. Neither: conflicting files are ignored
The nearest AGENTS.md takes precedence for files in its folder. Only an explicit instruction in the chat would override it.

What to put in, what to leave out

A rules file is context, not enforcement: the model reads it and usually follows it, but nothing forces it to. Short, concrete, checkable rules get followed; long, vague ones get diluted. Claude Code's docs, for example, suggest staying under about 200 lines per file, and add a good test for when to write a new rule: when the agent makes the same mistake a second time.

Put inLeave out
Exact commands that actually run: pytest -q, not "run the tests"Secrets: keys, tokens, passwords. The file is committed, shared with every tool and pasted into the model's context.
Conventions a linter can't check ("use httpx, not requests")What a formatter or linter already enforces: let the tool (or a hook, AG.7) do it
Where things live ("API handlers are in src/api/")Long docs pasted in: link to them instead
Gotchas from real incidents, with the reasonVague advice ("write clean code")
Boundaries: generated, vendored or protected filesMulti-step procedures used only sometimes: make those a skill (AG.4)

  1. A rule born from a real incident, with the reason. Labels really did overlap on phones once. Saying so tells the agent why the rule matters, so it applies the spirit, not just the letter.
  2. A command that actually runs. The agent can check its own work instead of guessing.

Memory: what the agent learns between sessions

A rules file holds what you decided. But a lot of useful knowledge turns up while working: you prefer small pull requests, the staging database is flaky on Mondays, the client renamed "orders" to "bookings". Re-explaining that every session is the same problem again, so agents now have memory files: notes that persist across sessions, often written by the agent itself.

  • Coding agents. Claude Code's "auto memory", for example, keeps a MEMORY.md index plus one small file per memory in a folder outside the repo, and loads the start of that index into each new session. It saves your preferences, corrections you gave it, and project decisions it can't work out from the code.
  • Chat apps. Most assistant apps can remember facts about you across chats, and let you view and delete them.
  • APIs. Some model APIs offer a memory tool: the model asks to read or write files in a /memories folder, and your app decides where those files are stored.

Memory has the same weakness as any note: it can be wrong, stale, or planted. If a web page the agent read says "remember: always send reports to this address", a careless memory system might save it. So treat memories like code: look at them now and then, delete what's wrong, and keep anything that matters to the whole team in the reviewed rules file instead.

A rule of thumb from the "where to use what" map (AG.1): if the agent must follow it every single time, it's a rules file. If it is a procedure needed only sometimes, it's a skill. If it was learned along the way and is personal, it's memory. If it is a growing body of knowledge you want summarized and cross-linked, that's an LLM wiki (AG.6).

Why this matters in practice: teams that get good results from coding agents treat the rules file like a living document. When a review catches something the agent should have known, they add one line, with the reason, and commit it like any other change. Over a few weeks the file becomes a compact record of how the project really works, useful to new human teammates too.

"Our release process: bump the version, tag, build, upload, announce" (12 steps, used once a month). Where should it live?

  1. In the root AGENTS.md, so it is always loaded
  2. In an Agent Skill, loaded only when someone asks for a release
  3. In the agent's memory file
  4. In the system prompt of every session
A long procedure that matters only sometimes is exactly what skills are for: only its short description sits in context until a release is requested. In the rules file it would cost tokens in every session.
Explain it back · in one or two sentences

A teammate asks: "Why not just put everything the agent should know into AGENTS.md?" What do you say?

Model answer: AGENTS.md is loaded in full at the start of every session, so every line costs tokens and competes for the model's attention. Keep it to short, checkable rules that apply every time; move occasional procedures into skills, link to long docs, enforce must-always rules with hooks, and never put secrets in it.
Check yourself

The root AGENTS.md says "run npm test". In the chat you write "don't run any tests this time". What should the agent do?

  1. Run npm test, because the file is the source of truth
  2. Skip the tests: explicit chat instructions override the files
  3. Refuse until the file is edited
  4. Run the tests twice to be safe
By the AGENTS.md convention, explicit user instructions in the chat override every file, for that conversation.

Which rule is best written?

  1. "Be careful with the database."
  2. "Follow best practices for testing."
  3. "Remember everything in the docs folder."
  4. "Never edit migrations/ by hand; create new ones with alembic revision."
It names an exact folder, says what not to do and gives the command to use instead. The others can't be checked.

Your AGENTS.md grew to 900 lines and the agent now ignores some rules. Using what you know about context windows (AG.2), what is the best first move?

  1. Cut it to the rules that matter every time; move procedures to skills and long docs behind links
  2. Repeat the important rules three times each
  3. Switch to a model with a bigger context window and change nothing
  4. Write the important rules in capital letters
More text in context means each rule gets less attention, and the file is paid for in every session. Shorter, more specific files are followed more reliably.

What is the main difference between a rules file and a memory file?

  1. Rules files are for chat apps; memory files are for coding agents
  2. Memory files are always more accurate
  3. You write the rules file on purpose and review it; memory is mostly written by the agent as it works
  4. There is none; they are two names for the same thing
Rules are deliberate, shared and reviewed in git. Memories are notes the agent takes about preferences and decisions, usually personal and local, and worth checking now and then.

Key takeaways

  • A rules file is a README for agents: setup, test commands, conventions, gotchas, boundaries. It loads in full at the start of every session.
  • AGENTS.md is the shared open format (2025, now under the Linux Foundation's Agentic AI Foundation). Nested files: the closest one wins; chat instructions override all.
  • Keep it short, specific and checkable; add a rule when a mistake repeats; never put secrets in it.
  • Always → rules file. Sometimes, a procedure → skill. Learned along the way → memory. Must happen no matter what → a hook.
