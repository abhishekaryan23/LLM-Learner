Prompt, RAG or fine-tune?

Lesson 6 of Building with LLMs

Your model doesn't do what you need. You can tell it more (prompting), let it look things up (RAG), or train it (fine-tuning). Picking the wrong one can cost a team months. This lesson gives you the one distinction that settles most cases, a decision guide you can click through, and the cost arithmetic behind "fine-tune a smaller model".

By the end you can

  • Say what prompting, RAG and fine-tuning each change, and compare their cost and update cycle.
  • Decide which to use (or how to combine them) from five questions: knowledge or behaviour, freshness, format, latency and cost, and data.
  • Compare the per-query cost of a long prompt on a big model with a small fine-tuned model, and explain distillation.
Prerequisites: SY.3 Retrieval-augmented generation (what RAG does and costs) and M3.7 LoRA & QLoRA (how fine-tuning is done cheaply). Helpful but optional: AG.1 Where to use what, the wider map this lesson zooms into, and M5.2 Distillation & pruning.
Warm-up · guess before you learn

Take your best guess. A wrong guess now makes the right answer stick later.

A bot must answer from your product catalogue, which changes every day. What fits best?

  1. Retrieve the relevant catalogue entries for each question (RAG)
  2. Fine-tune the model on the catalogue every night
  3. A longer system prompt saying "be accurate"
  4. A bigger model
Fresh, specific facts are RAG's home ground: update the index and the next question sees the change. Nightly fine-tuning is slow and costly, and models don't reliably memorise exact facts from fine-tuning.

You need a model to write every reply in a precise house style, millions of times a day, as cheaply as possible. You have 5,000 example replies. What fits best?

  1. RAG over the 5,000 replies
  2. A big model with all 5,000 examples in the prompt
  3. Fine-tune a smaller model on the examples
  4. Nothing can enforce a style
Style is behaviour, not knowledge, and at that volume the per-query cost of a long prompt adds up. A small fine-tuned model learns the style from examples and needs only a short prompt.

Three levers, and what each one changes

When GPT-3 arrived in 2020, Brown et al. showed that a large model could do a new task from a few examples in the prompt, with no training: in-context learning. Before that, adapting a model meant fine-tuning it, as everyone did with BERT. The same year, Lewis et al. introduced retrieval-augmented generation, which fetched documents and fed them to the model as it answered. Then LoRA (Hu et al., 2021) and QLoRA (2023) made fine-tuning cheap enough for almost anyone (M3.7). By 2023 every team building on LLMs faced the same question: which lever do we pull?

The one distinction that settles most cases: prompting and RAG change what the model reads; fine-tuning changes what the model is. Step through it:

ChangesWhat the model reads: instructions, examplesWhat the model reads: passages fetched per questionThe weights (often a LoRA adapter)

Always start with the cheapest lever. Write a clear prompt (SY.1), build a small eval set (M4.7) and measure. Pull the next lever only for the failures the prompt can't fix, and keep measuring with the same evals.

Which of these changes the model's weights?

  1. Adding five worked examples to the system prompt
  2. Training a LoRA adapter on 2,000 example replies
  3. Retrieving three help articles per question
  4. Putting the most important instruction at the end of the prompt
Only training changes weights. Examples, retrieved articles and instruction order are all text in the context window: remove them and the model is unchanged.

When RAG wins, when fine-tuning wins

Ask first: is the gap knowledge (facts the model doesn't have) or behaviour (how it answers)?

Knowledge → RAG. The evidence is consistent. Ovadia et al. (2023, "Fine-Tuning or Retrieval?") injected new facts into models both ways and found that RAG beat unsupervised fine-tuning, for facts the model had seen before and for entirely new ones. Gekhman et al. (2024) found that fine-tuning examples with new facts were learned slowly, and once learned they made the model more prone to hallucinate. Their reading: models get most of their facts in pretraining, and fine-tuning mostly teaches them how to use what they know. RAG also gives you what fine-tuning can't:

  • Freshness: change a document, re-index it, and the next answer uses it.
  • Citations: the answer can point to its source, so users and reviewers can check it.
  • Access control: retrieve only documents this user may see. Facts baked into weights are visible to everyone who uses the model.

Behaviour → fine-tuning, once prompting runs out. Fine-tuning wins when:

  • Format or style must hold every time, and prompting gets it right only most of the time: a house voice, a strict report layout, a domain's jargon.
  • The task is narrow and high-volume: classify tickets, extract fields, route requests. A small fine-tuned model often matches a big general one there.
  • Latency or cost matters: a smaller model with a short prompt answers faster and cheaper than a big model with pages of instructions (the next bytes do the arithmetic).
  • The prompt is huge: dozens of examples needed in every request can often be trained in instead.

Combining them is common and natural, because they fix different things. A fine-tuned model can still read retrieved passages. RAFT (Zhang et al., 2024) went further: it fine-tuned models on questions paired with retrieved documents, including irrelevant "distractor" ones, so they learned to answer from the useful passage and ignore the rest.

One more option often beats fine-tuning for format: many APIs now offer structured outputs, which force the reply to match a JSON schema by constraining decoding (SY.4). If the "format" you need is machine-readable, try that first.

Explain like I'm 5

A new helper starts at a toy shop. There are three ways to help them do well.

You can give them a note: "Smile, say hello, and keep it short." That's prompting. You can give them the shop's big binder to look up prices whenever someone asks. That's RAG, and when a price changes you just swap the page. Or you can send them on a training course, so being friendly and quick becomes a habit. That's fine-tuning.

The binder is best for prices, because prices change. The course is best for habits, because a habit doesn't need a note every time. Good shops use all three.

Where it breaks: a person who takes a course also remembers the facts they learned there. A model fine-tuned on facts learns them slowly and patchily, and can start making up facts that sound similar.

A legal-research assistant must quote the exact wording of the newest regulations and show where each quote came from. What is the core of the solution?

  1. Fine-tune on all regulations each quarter
  2. A system prompt asking for exact quotes
  3. A larger model, which knows more law
  4. RAG over the current regulations, with citations
Exact, current, citable text is knowledge, which is RAG's strength. Fine-tuning doesn't reliably memorise exact wording, can't cite and goes stale between training runs. A larger model still has a training cutoff.

The decision guide

Five questions settle most cases. Click through them with your own project in mind; the picture shows which levers to pull, and the reasons appear below it.

Playground: prompt, RAG or fine-tune?

Solid orange: recommended. Dashed: worth considering, or later. The rules are a rule of thumb; your evals have the final word.

1. What is the model missing?

2. How often does the knowledge change?

3. Do you need a strict format or style?

4. Latency and cost?

5. How many good input → output examples do you have?

The guide encodes a few rules worth remembering:

  • Prompting first, always, with an eval set to measure everything else against.
  • Knowledge → RAG. If it's small and stable enough to fit in a few thousand tokens, just put it in the prompt and cache it. For a small, evolving body of knowledge you want summarised and cross-linked once: an LLM wiki (AG.6).
  • Behaviour that prompting can't hold, with hundreds of examples or more → fine-tuning. Typical fine-tuning sets run from a few hundred to tens of thousands of examples; quality matters more than quantity.
  • Behaviour with little data → few-shot prompting now. If it is a procedure needed only sometimes, an Agent Skill (AG.4); if it is a convention for every task in a coding agent, a rules file (AG.5).
  • Tight latency or cost → a smaller model. Fine-tuning (often by distillation) is what makes a small model good enough.

The map in AG.1 puts it in one line: "Change the model's built-in behaviour, style or cost at scale" is the row for fine-tuning; everything about facts goes elsewhere.

You need strict JSON output and have only 20 examples. What should you try before fine-tuning?

  1. Structured outputs (schema-constrained decoding) if the API offers them, plus a few examples in the prompt
  2. RAG over the 20 examples
  3. An LLM wiki
  4. Nothing; 20 examples is plenty for fine-tuning
A schema constraint makes valid JSON a guarantee rather than a habit, and a few examples show what good content looks like. Twenty examples is thin for fine-tuning; save them as eval cases.

The cost arithmetic: long prompt vs small fine-tuned model

Per-query cost is tokens times price, for input and output separately:

$$\text{cost per query} = \frac{T_{\text{in}} \, P_{\text{in}} + T_{\text{out}} \, P_{\text{out}}}{10^6}$$

Here $T_{\text{in}}$ and $T_{\text{out}}$ are the input and output tokens, and $P_{\text{in}}$ and $P_{\text{out}}$ are the prices per million tokens. Prices vary by provider and fall over time, so the numbers below are illustrative, not quotes.

Worked example

A support bot. Option A: a big model at $\$2.50$ per million input tokens and $\$10$ per million output tokens, with a 10,000-token prompt (instructions plus many examples) and 200-token replies. Option B: a small fine-tuned model at $\$0.30$ in and $\$1.20$ out, which needs only a 400-token prompt for the same replies.

  1. A per query: $(10{,}000 \times 2.50 + 200 \times 10) / 10^6 = (25{,}000 + 2{,}000)/10^6 = \$0.027$
  2. B per query: $(400 \times 0.30 + 200 \times 1.20) / 10^6 = (120 + 240)/10^6 = \$0.00036$, 75 times cheaper.
  3. At 1 million queries a month: about $\$27{,}000$ for A against $\$360$ for B.
  4. Break-even: if building B costs $\$2{,}000$ once (data, training runs, evals), it pays for itself after $2{,}000 / (0.027 - 0.00036) \approx 75{,}000$ queries.

Two honest caveats. First, prompt caching (AG.2) cuts A's bill: if 9,600 of its tokens are a cached prefix billed at a tenth of the price, A costs about $\$0.0054$, so B's advantage drops from 75× to about 15×. Second, B has costs A doesn't: someone must maintain the training set, retrain when the base model is updated and re-run the evals. At low volume, the big model with a good prompt is usually the right answer.

Distillation: how the small model gets good

Where do you get thousands of perfect replies for option B? Often from option A. Distillation (Hinton et al., 2015; M5.2) trains a small "student" model to imitate a large "teacher". For LLM products the usual recipe is simple: run the big model with your best prompt on thousands of real inputs, filter its outputs with your evals (and humans where it matters), and fine-tune the small model on what's left. The student learns the teacher's behaviour on your task, without the long prompt. Check the teacher model's terms of use first: some providers restrict using outputs to train other models.

In real practice: most production systems in 2026 are prompting plus retrieval, and a minority add fine-tuning, usually for one of three reasons: a strict output format or voice, a narrow high-volume task, or moving to a smaller, cheaper model by distillation. Teams that fine-tune "to teach the model our documents" tend to switch to RAG. And whichever lever you pull, the same eval set decides whether it worked.

In the worked example, prompt caching makes option A about 5 times cheaper. What happens to the case for fine-tuning a small model?

  1. It disappears entirely; caching makes every prompt free
  2. Nothing changes; caching doesn't affect cost
  3. It weakens (B is now about 15× cheaper, not 75×), so break-even needs more volume
  4. It gets stronger, because cached prompts are slower
Caching discounts the repeated prefix, so the long prompt costs much less, though not zero. The gap narrows, the break-even volume rises, and at moderate volume the simpler option A may win.
Explain it back · in two or three sentences

A manager says: "Let's fine-tune the model on our wiki so it knows everything about our company." What do you tell them, and when would you fine-tune?

Model answer: Fine-tuning changes the model's habits, not a reliable store of facts: new facts are learned slowly, can increase hallucination, go stale as the wiki changes and can't be cited. For company knowledge, use RAG (or, for a small, evolving set, an LLM wiki), which reads the current text at question time and can cite it. Fine-tune when the problem is behaviour, such as a strict format, a house style or a narrow high-volume task, or to make a smaller, cheaper model good enough, ideally with hundreds to thousands of examples and an eval set to prove it helped.
Check yourself

What did Gekhman et al. (2024) find about fine-tuning on facts the model didn't already know?

  1. New facts were learned faster than known ones
  2. They were learned slowly, and once learned they increased the model's tendency to hallucinate
  3. They had no effect at all
  4. They erased all of the model's other knowledge
Their conclusion: models get most factual knowledge in pretraining, and fine-tuning mainly teaches them to use it. That is why facts belong in retrieval.

Connect to M3.7: why does LoRA make "fine-tune a small model per task" practical?

  1. LoRA adapters store the task's documents
  2. LoRA removes the need for training data
  3. LoRA makes the base model smaller
  4. It trains only small low-rank matrices, so training is cheap and many task adapters can share one base model
With the base frozen, training needs far less memory, and each adapter is megabytes rather than a full model copy. Serving systems can switch adapters per request.

Which situation is the strongest case for combining RAG with fine-tuning?

  1. High-volume answers from changing documents in a strict house style, where a small model must be fast
  2. A prototype used by five people
  3. A question-answering bot over ten static FAQ entries
  4. A one-off summary of a single report
Changing documents call for retrieval; strict style at high volume on a small model calls for fine-tuning. The other cases are served by a good prompt (with the FAQ pasted in and cached).

Option A costs $\$0.02$ per query and option B $\$0.001$. B needs a one-off $\$3{,}800$. After how many queries does B pay off?

  1. 3,800
  2. 19,000
  3. 200,000
  4. 3.8 million
The saving is $0.02 - 0.001 = 0.019$ dollars per query, and $3{,}800 / 0.019 = 200{,}000$ queries.

Key takeaways

  • Prompting and RAG change what the model reads; fine-tuning changes what it is.
  • Start with a prompt and an eval set. Knowledge (fresh, private, citable) → RAG. Behaviour (format, style, narrow tasks) that prompting can't hold → fine-tuning.
  • Fine-tuning is a poor way to teach facts: they're learned slowly, can raise hallucination and go stale.
  • Cost per query is $(T_{\text{in}}P_{\text{in}} + T_{\text{out}}P_{\text{out}})/10^6$. A small fine-tuned model with a short prompt can be far cheaper at high volume; caching narrows the gap.
  • Distillation: generate and filter outputs from a big model, then fine-tune a small one. Combine levers freely; they fix different things.
