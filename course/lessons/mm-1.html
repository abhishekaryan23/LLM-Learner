Connecting vision to LLMs

Lesson 1 of Multimodal models

Most of the AI models that “look at” your photo, screenshot or PDF are, at heart, a text LLM with a pair of eyes bolted on. The bolt is surprisingly small: a projector that turns image patches into visual tokens the LLM reads like words. This lesson builds that recipe piece by piece and counts what an image costs.

By the end you can

  • Trace an image through vision encoder → projector → LLM, and compute how many visual tokens it becomes.
  • Compare three ways to connect vision to a language model: Flamingo's cross-attention, BLIP-2's Q-Former and LLaVA's projector.
  • Explain the two training stages (align, then instruction-tune) and how tiling or dynamic resolution handle large images.
Prerequisites: V1.2 Contrastive learning & CLIP (the vision encoder we plug in) and M1.4 The decoder-only transformer (the LLM it plugs into). Helpful but optional: V1.1 Vision Transformers, for how an image becomes a grid of patches.

$336 / 14 = 24$ patches per side, so $24 \times 24 = 576$. In a LLaVA-style model each patch becomes one token in the LLM's input, so this one small image costs 576 tokens.

In 2023 a simple recipe made many open models able to chat about images. What did it add to an existing text LLM?

  1. Nothing: it retrained the whole LLM from scratch on images
  2. A small learned layer that maps image-patch features into the LLM's word-embedding space
  3. A captioning model whose text description is pasted into the prompt
  4. New image words added to the tokenizer's vocabulary
That is LLaVA's projector. Pasting a caption (option 3) was an earlier trick and works, but the caption throws away most of what's in the picture.

From captions to visual tokens

By 2021 there were strong text LLMs (GPT-3) and strong image encoders (CLIP, V1.2), but they lived apart. Vision-language systems were mostly task-specific: one model for captions, another for visual question answering. The quickest bridge was text itself: caption the image, then paste the caption into the prompt. PICa (Yang et al., 2022) answered questions about images this way with GPT-3. It works, but a caption is a bottleneck. Ask about the colour of the third car or a number on a sign, and if the captioner didn't mention it, the LLM can't know.

The better idea is to skip the words and feed the LLM the image's features directly. Frozen (Tsimpoukelli et al., 2021) showed that a vision encoder trained to output a few “prefix” embeddings could steer a frozen language model. Since 2023 the standard recipe has three parts:

  1. Vision encoder: a pretrained image model, usually a CLIP-style ViT (CLIP itself or, in many open models since 2024, SigLIP; Zhai et al., 2023), that turns each image patch into a feature vector.
  2. Connector (often a projector): a small network that maps those features into the LLM's embedding space.
  3. LLM: a pretrained decoder that reads the resulting visual tokens alongside ordinary text tokens and writes the answer.

Why does this work at all? An LLM's input is just a sequence of vectors (M1.4). It never sees token IDs past the embedding lookup. Hand it vectors that live in the same space and carry useful information, and attention will use them like any other context.

Explain like I'm 5

A robot with a camera for a head is great at looking at photos, but it can't talk. A wise owl knows lots of things, but it can only read.

So a parrot interpreter sits between them. For every photo the robot holds up, the parrot strings a row of coloured beads in the owl's own bead language. The owl reads the beads like a sentence and answers your question.

The robot is the vision encoder, the parrot is the projector, the beads are visual tokens and the owl is the LLM. The parrot is the only one who has to learn something new.

Where it breaks: the owl doesn't just read the beads passively. During instruction tuning the owl itself also learns to use them better.

Why can an LLM accept visual tokens at all, even though it was trained on text?

  1. Its layers only ever see vectors; any vector in the embedding space can sit in the sequence and be attended to
  2. The image is first converted to words by the vision encoder
  3. Its tokenizer already contains one token per pixel colour
After the embedding lookup, a transformer works on vectors only. The projector's job is to produce vectors in that same space, so the LLM can attend to them like text.

Counting visual tokens

A ViT cuts an $H \times W$ image into square patches of side $p$ pixels (V1.1). In the LLaVA recipe each patch becomes one visual token, so

$$N_{\text{visual}} = \frac{H}{p} \times \frac{W}{p}$$

where $H$ and $W$ are the image height and width in pixels after resizing, $p$ is the patch side, and $N_{\text{visual}}$ is the number of tokens the LLM must read. Tokens grow with the square of the side: double the resolution, four times the tokens. And because attention compares every token with every other, the cost of the attention scores grows with the square of the sequence length.

Worked example

LLaVA-1.5 uses CLIP ViT-L/14 at 336×336 pixels.

  1. Patches per side: $336 / 14 = 24$.
  2. Visual tokens: $24 \times 24 = 576$.
  3. Its LLM has a 4,096-token context, so one image uses $576 / 4096 \approx 14\%$ of it, before you type a word.

Three ways to connect: cross-attention, Q-Former, projector

The connector is where designs differ most. Three landmark models span the options.

Flamingo (Alayrac et al., 2022, DeepMind) kept a 70B Chinchilla language model completely frozen. A Perceiver resampler squeezed each image's features into a fixed 64 vectors, and new gated cross-attention layers, inserted between the frozen LM layers, let text attend to them:

$$y \leftarrow y + \tanh(\alpha)\cdot \mathrm{XAttn}(y,\ v)$$

Here $y$ is the text stream at that layer, $v$ the resampled visual vectors, $\mathrm{XAttn}$ cross-attention (queries from text, keys and values from the image), and $\alpha$ a learned gate that starts at 0. At initialisation $\tanh(0) = 0$, so the model behaves exactly like the original LM and learns to let vision in gradually. Trained on web pages with interleaved images and text, Flamingo could learn new visual tasks from a few examples in the prompt.

BLIP-2 (Li et al., 2023, Salesforce) froze both the image encoder and the LLM and trained a small bridge in between, the Q-Former. It has 32 learned query vectors that cross-attend to the image features and come out as 32 “soft prompt” vectors for the LLM. Every image costs the same 32 tokens, and only about 188M parameters are trained.

LLaVA (Liu et al., 2023, “Visual Instruction Tuning”) went the other way: no resampling at all. A single linear layer maps each CLIP patch feature $z_i$ into the LLM's embedding space, $h_i = W z_i$. In LLaVA-1.5 (Liu et al., 2023) this became a two-layer MLP, the encoder moved to 336 pixels, and the whole model trained in about a day on one 8-GPU node. Every patch survives as its own token, so nothing is thrown away before the LLM sees it, at the price of many more tokens.

  • Fixed small budget (Flamingo's 64, BLIP-2's 32): cheap, but fine detail such as small text can be squeezed out.
  • One token per patch (LLaVA): simple and detail-preserving, but token-hungry.

As of 2026, most open vision-language models follow the LLaVA pattern (encoder, MLP projector, LLM), often with some token merging. Cross-attention never disappeared: Meta's Llama 3.2 Vision models (2024) add cross-attention adapter layers to a Llama 3.1 text model. For closed frontier models, labs mostly don't publish their connectors.

Why does Flamingo's gate $\tanh(\alpha)$ start with $\alpha = 0$?

  1. To make the visual signal as strong as possible from the first step
  2. So that at the start the frozen LM behaves exactly as before, and vision is blended in gradually during training
  3. Because tanh can't be computed for other values
$\tanh(0) = 0$ switches the new cross-attention off at first, so training starts from the intact language model instead of disrupting it with random visual noise.

Training: align first, then instruction-tune

A freshly initialised projector outputs vectors the LLM has never seen: noise, as far as the LLM is concerned. LLaVA fixes this in two stages.

  1. Stage 1, feature alignment. Freeze the vision encoder and the LLM; train only the projector on image–caption pairs (about 595K pairs filtered from CC3M in LLaVA, 558K captioned images in LLaVA-1.5). The task: given the visual tokens, predict the caption. The projector learns to put each image “where its words are” in embedding space.
  2. Stage 2, visual instruction tuning. Keep the encoder frozen, train the projector and the LLM on image-grounded conversations. LLaVA's 158K examples were written by a text-only GPT-4 that was given each image's captions and object boxes; LLaVA-1.5 mixed in academic VQA data for about 665K examples.

Both stages use the ordinary next-token loss (M2.2), counted only on the tokens the model should produce:

$$\mathcal{L} = -\sum_{t \in \text{answer}} \log p_\theta\big(x_t \mid x_{<t},\ \text{image}\big)$$

$x_t$ is the $t$-th answer token, $x_{<t}$ everything before it (visual tokens, question, earlier answer tokens), and $\theta$ the parameters being trained in that stage. Visual and question tokens are inputs only; they're masked out of the loss, just as the prompt is in supervised fine-tuning (M3.1).

Why two stages? Alignment is cheap and needs only captions, while conversation skills need curated data and touch the LLM itself. Training both from the start would let a random projector push noisy gradients into the LLM. Recipes published since 2024 typically add stages (unfreezing the vision encoder, large interleaved and OCR data, then preference tuning), but the align-then-tune skeleton is the same.

In LLaVA's stage 1, which parts are trained?

  1. Only the projector; the vision encoder and LLM are frozen
  2. Only the LLM; the projector is fixed at random values
  3. Everything, end to end, on instruction data
Stage 1 is alignment: with both big models frozen, only the projector learns to map image features to where the matching caption words live.

High resolution: tiles and dynamic resolution

A 336-pixel encoder is fine for “is there a dog?” and hopeless for a receipt or a slide full of small text: shrink a full page to 336×336 and each line of text is a few pixels tall. But CLIP-style encoders were trained at one fixed size. Two families of fixes emerged.

Tiling. LLaVA-NeXT (LLaVA-1.6, Liu et al., 2024) keeps the 336-pixel encoder and cuts a larger image into a grid of 336×336 tiles, plus one downscaled overview of the whole image for global context, choosing the grid to fit the aspect ratio (up to 672×672, 336×1344 or 1344×336). A 672×672 image is 2×2 tiles plus the overview: $5 \times 576 = 2{,}880$ visual tokens. Detail is back; the bill is five times higher.

Dynamic (native) resolution. Qwen2-VL (Wang et al., 2024) instead lets its ViT read images at roughly their own size and shape, with 2-D rotary position embeddings so the encoder knows where each patch sits, then merges each 2×2 block of 14-pixel patches into one token. One token then covers 28×28 pixels: a 224×224 image becomes $8 \times 8 = 64$ tokens (66 with the start and end markers), and a 1344×1344 image becomes $48 \times 48 = 2{,}304$. Users set minimum and maximum pixel budgets to trade detail for cost.

Both approaches share the same economics: detail costs tokens. Tokens cost memory (each one sits in the KV cache, M1.5), latency and money. Much current work is about spending them wisely: merging or pruning redundant tokens (a blue sky does not need 200 of them) and choosing resolution per image.

Why this matters in practice: hosted multimodal APIs generally bill an image as input tokens, and the count grows with resolution, so a phone photo can quietly cost more than a page of text. Resizing or cropping to what the question needs is often the cheapest optimisation you have. For documents and screenshots, though, too little resolution makes small text unreadable (MM.3), so test accuracy before you downscale.

What is the extra “overview” image for in LLaVA-NeXT's tiling?

  1. It replaces the tiles when the image is small
  2. It is used only for training, never at inference
  3. Tiles each see only a piece; the downscaled overview gives the model the global layout of the whole image
Each tile is encoded on its own, so no single tile sees the whole picture. The low-resolution overview restores global context for 576 extra tokens.
Explain it back · in two or three sentences

A friend asks how a chatbot that was trained on text can answer questions about a photo. Explain the pipeline and what had to be trained.

Model answer: A pretrained vision encoder (usually a CLIP-style ViT) turns the image's patches into feature vectors, and a small projector maps each one into the LLM's embedding space, producing visual tokens that sit in the sequence next to the text tokens. The LLM attends over all of them and writes the answer. Training first aligns the projector on image–caption pairs with everything else frozen, then instruction-tunes the projector and LLM on image-grounded conversations.
Check yourself

Which description matches LLaVA's connector?

  1. 32 learned queries cross-attend to the image and become 32 soft-prompt tokens
  2. Gated cross-attention layers inserted between frozen LM layers
  3. The image is captioned and the caption is added to the prompt
  4. A linear layer (an MLP in LLaVA-1.5) maps each patch feature to one token in the LLM's embedding space
Option 1 is BLIP-2's Q-Former, option 2 is Flamingo, option 3 is the older caption pipeline. LLaVA keeps one token per patch and just projects it.

Recall the causal mask in a decoder-only LLM (M1.4). Why do most VLM prompts put the image before the question?

  1. Visual tokens must be first or the projector fails
  2. Each token can only attend to earlier tokens, so the question and the answer can attend to the image only if it comes first
  3. It reduces the number of visual tokens
  4. The order makes no difference in a transformer
With causal masking, information flows only forward. Image first means every question and answer token can look back at all the visual tokens.

A tiling model uses 336-pixel tiles (576 tokens each) plus one overview. How many visual tokens does a 1008×672 image cost?

  1. 576
  2. 3,456
  3. 4,032
  4. 6,048
$1008/336 = 3$ by $672/336 = 2$ gives 6 tiles, plus 1 overview: $7 \times 576 = 4{,}032$. 3,456 forgets the overview.

Why not train the projector and the LLM together from the very first step?

  1. A random projector feeds the LLM noise, and its gradients can damage the LLM before the projector has learned anything useful
  2. The LLM has no gradients
  3. Image–caption pairs can't be used with a next-token loss
  4. It is impossible to unfreeze an LLM after pretraining
Aligning the projector first (stage 1) gives the LLM sensible inputs before its own weights start to move in stage 2.

Key takeaways

  • Most vision-language models are vision encoder → connector → LLM; the LLM reads visual tokens like words.
  • One token per patch: $N = (H/p)(W/p)$. A 336×336 image with 14-pixel patches is 576 tokens; doubling the side quadruples it.
  • Connectors range from Flamingo's gated cross-attention and BLIP-2's 32-query Q-Former to LLaVA's simple linear/MLP projector.
  • Train in two stages: align the projector with everything else frozen, then instruction-tune projector and LLM.
  • High resolution comes from tiles (LLaVA-NeXT) or dynamic resolution with token merging (Qwen2-VL); either way, detail costs tokens.
