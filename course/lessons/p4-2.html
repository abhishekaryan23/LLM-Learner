A training loop

Lesson 2 of PyTorch in an hour

Every model in this course, from a straight line to a frontier LLM, is trained by the same five lines of PyTorch, repeated: zero the gradients, run the model, compute the loss, backpropagate, step.

By the end you can

  • Write a model as an nn.Module and pick a loss and an optimizer for it.
  • Write the five-line training loop from memory and say what each line does.
  • Use a DataLoader for mini-batches, switch between train and eval mode, and log useful numbers.
Builds on: P4.1 Tensors & autograd (.backward(), .grad, no_grad), P2.2 Gradient descent (mini-batches, learning rate) and P2.4 Overfitting & data splits (validation, dropout).
Warm-up · guess before you learn

Take your best guess. Being wrong now helps the right answer stick later.

Put these in the order a training step runs them: (a) loss.backward(), (b) optimizer.step(), (c) pred = model(x), (d) optimizer.zero_grad().

  1. c, b, a, d
  2. a, c, d, b
  3. b, d, c, a
  4. d, c, a, b
Clear old gradients, run forward, backpropagate, then update. You can't backpropagate before the forward pass has built the graph, and you can't step before the gradients exist.

Your model uses dropout. You evaluate it on the validation set but forget to call model.eval(). What happens?

  1. Nothing; dropout only matters for the gradients
  2. Dropout keeps randomly zeroing activations, so validation scores come out noisy and usually worse
  3. PyTorch raises an error
  4. The model trains on the validation set
Train/eval mode switches the behaviour of layers like dropout (P2.4) and batch norm. It doesn't change gradient tracking; that's what torch.no_grad() is for.

The ingredients

1. A model: nn.Module

A model is a class that subclasses nn.Module. You create its layers in __init__ and say how data flows through them in forward. Any nn.Parameter inside, including the weights of built-in layers like nn.Linear, is registered automatically, so model.parameters() can hand all of them to the optimizer.

import torch
from torch import nn

class TinyClassifier(nn.Module):
    def __init__(self, d_in, d_hidden, n_classes):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(d_in, d_hidden),
            nn.ReLU(),
            nn.Dropout(p=0.1),
            nn.Linear(d_hidden, n_classes),
        )

    def forward(self, x):
        return self.net(x)    # logits: (B, n_classes)

model = TinyClassifier(2, 32, 3)
sum(p.numel() for p in model.parameters())   # 195

Call the model like a function, model(x), not model.forward(x): the call runs PyTorch's hooks around forward.

2. A loss

For classification, nn.CrossEntropyLoss() takes raw scores (logits, shape (B, C)) and integer class labels (shape (B,)). It applies the softmax internally, so don't add one yourself. The result is the average of $-\ln p_{\text{correct}}$ over the batch (P2.1). For regression, use nn.MSELoss(). An LLM uses the very same cross-entropy: its logits of shape (B, T, V) are flattened to (B·T, V) so that every token position counts as one classification.

3. An optimizer

loss_fn = nn.CrossEntropyLoss()
opt = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=0.01)

The optimizer holds references to the parameters and knows how to update them from their .grad. torch.optim.SGD is the plain $\theta \leftarrow \theta - \eta\,\nabla L$ from P2.2; AdamW is what LLMs use (M2.3).

4. Batches: DataLoader

from torch.utils.data import TensorDataset, DataLoader

train_ds = TensorDataset(X_train, y_train)
train_loader = DataLoader(train_ds, batch_size=64, shuffle=True)

Iterating over train_loader yields mini-batches (xb, yb), reshuffled every epoch. With 1,000 examples and batch_size=64 that's 16 batches per epoch (the last one has only 40 examples, unless you pass drop_last=True).

The loop

for epoch in range(20):
    model.train()                       # dropout on
    for xb, yb in train_loader:
        opt.zero_grad()                 # 1. clear old gradients
        logits = model(xb)              # 2. forward
        loss = loss_fn(logits, yb)      # 3. one number
        loss.backward()                 # 4. fill every .grad
        opt.step()                      # 5. update parameters

    model.eval()                        # dropout off
    with torch.no_grad():               # no graph needed
        val_logits = model(X_val)
        val_loss = loss_fn(val_logits, y_val).item()
        val_acc = (val_logits.argmax(dim=1) == y_val).float().mean().item()
    print(f"epoch {epoch}: val loss {val_loss:.3f}, acc {val_acc:.1%}")

On three well-separated clusters of 2-D points, this reaches about 98% validation accuracy within a few epochs on a laptop CPU. A few details carry most of the weight:

  • model.train() / model.eval() switch layer behaviour (dropout, batch norm). They do not turn off gradients; torch.no_grad() does that. Evaluation needs both.
  • .item() turns a one-element tensor into a Python number. Log with it, not with the tensor: keeping the tensor around would keep its whole graph alive in memory.
  • Devices: move the model once (model.to(device)) and each batch as it arrives (xb, yb = xb.to(device), yb.to(device)).
Explain like I'm 5

Learning to shoot hoops. Each round: forget what the coach said last time (zero the gradients), shoot a handful of balls (forward), count how far you missed (loss), hear the coach say "aim a bit left, a bit softer" (backward), and adjust (step). Then the next handful of balls.

Do that for hours and you're good. Where the analogy breaks: a model gets exact, numeric advice for every single "muscle" (parameter) at once, millions of them, every round.

Worked example: counting steps

50,000 training examples, batch_size=128, 10 epochs, plain SGD with lr $= 0.1$.

  1. Batches per epoch: $\lceil 50{,}000 / 128 \rceil = \lceil 390.6 \rceil = 391$ (the last batch is partial).
  2. Optimizer steps in total: $391 \times 10 = 3{,}910$. One opt.step() per batch.
  3. One step on a weight $w = 0.5$ with w.grad $= 2$: $w \leftarrow 0.5 - 0.1 \times 2 = 0.3$.

What an LLM training loop adds

The five lines don't change; what grows around them does:

  • Gradient clipping between backward and step rescales the gradients if their total norm exceeds a limit (often 1.0), which protects against rare loss spikes: 
    loss.backward()
nn.utils.clip_grad_norm_(model.parameters(), 1.0)
opt.step()
  • A learning-rate schedule (warm-up, then decay), stepped once per optimizer step (M2.3).
  • Mixed precision: running the forward pass in bfloat16 under torch.autocast (M2.5).
  • Gradient accumulation: calling backward() on several micro-batches before one step() to simulate a bigger batch. It works precisely because .grad accumulates; just divide each micro-batch loss by the number of micro-batches.
  • Distributed training across many GPUs (M2.5), checkpointing the model and optimizer state, and logging the loss, learning rate and gradient norm every step.
Why this matters for LLMs: pretraining (M2), fine-tuning (M3.1) and even DPO (M3.4) are this same loop with a different dataset and a different loss. A typical pretraining step might process a batch of about a million tokens, for example 512 sequences of 2,048 tokens. When a run misbehaves, the first suspects are in these five lines: a missing zero_grad, a forgotten model.eval(), a loss on the wrong shapes, or a learning rate that's too high.
Explain it back · in two or three sentences

Write the five lines of the inner loop from memory, and say in one phrase what each does.

Model answer: opt.zero_grad() clears the previous gradients; pred = model(xb) runs the forward pass and records the graph; loss = loss_fn(pred, yb) reduces the batch to one number; loss.backward() backpropagates and fills every parameter's .grad; opt.step() updates the parameters from those gradients.
Check yourself

Which pair do you need for a correct evaluation pass on a model with dropout?

  1. model.train() and torch.no_grad()
  2. model.eval() alone
  3. model.eval() and torch.no_grad()
  4. opt.zero_grad() and model.eval()
eval() switches dropout off; no_grad() stops autograd recording, saving memory and time. They're independent switches.

A classifier's last layer outputs logits of shape (32, 10). What should you pass to nn.CrossEntropyLoss() along with them?

  1. Integer class labels of shape (32,)
  2. Softmax probabilities of shape (32, 10)
  3. Labels of shape (10,)
  4. The argmax of the logits
The loss takes raw logits plus one integer label per example; it applies the (log-)softmax itself. Passing probabilities would apply softmax twice.

You remove opt.zero_grad() from the loop. What goes wrong?

  1. Nothing; the optimizer clears gradients in step()
  2. Each step uses the sum of all gradients so far, so updates grow and training drifts or diverges
  3. The model stops recording the graph
  4. PyTorch raises an error on the second backward()
.grad accumulates (P4.1), so the "gradient" becomes a running sum of stale gradients from earlier batches.

Your training loss keeps falling but validation loss started rising several epochs ago (P2.4). With this loop, what's the simplest fix?

  1. Remove model.eval() so validation matches training
  2. Raise the learning rate
  3. Evaluate on the training set instead
  4. Save a checkpoint whenever validation loss improves and keep the best one (early stopping); consider more weight decay or dropout
The validation numbers you log each epoch are exactly what early stopping needs. Hiding the gap doesn't fix it.

Key takeaways

  • Model = nn.Module with layers in __init__ and the data flow in forward.
  • The inner loop: zero_grad → forward → loss → backward → step, once per mini-batch.
  • DataLoader serves shuffled mini-batches; one pass over the data is an epoch.
  • model.train()/model.eval() switch dropout and similar layers; torch.no_grad() switches off autograd. Evaluation needs both.
  • LLM training is the same loop plus clipping, LR schedules, mixed precision and many GPUs.
