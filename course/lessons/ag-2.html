Context engineering: what the model sees

Lesson 2 of The agent toolkit

A model can only use what is in front of it, and the space in front of it is limited. Context engineering is the craft of deciding what goes into that space, when, and what gets thrown out. It matters more for an agent's quality than almost any other choice you make.

By the end you can

  • List what competes for an agent's context window and estimate a token budget.
  • Explain why long, cluttered context makes answers worse (“lost in the middle”, context rot).
  • Pick techniques that keep context lean: short instructions, just-in-time retrieval, progressive disclosure, compaction, notes, subagents and prompt caching.

The context window is working memory, with a budget

Early models had tiny windows. GPT-3 (2020) could see 2,048 tokens, a few pages. Builders spent their effort squeezing prompts to fit. Then windows exploded: 128k tokens for GPT-4 Turbo and 200k for Claude 2.1 (both November 2023), and a million for Gemini 1.5 (February 2024). The problem seemed solved: just put everything in.

It wasn't. Agents that run for an hour fill even huge windows, and answers got worse long before the limit. By mid-2025 people had a name for the craft of managing this: context engineering. Anthropic's engineering post Effective context engineering for AI agents (September 2025) defines it as curating and maintaining the best set of tokens for the model at each step. Prompting (SY.1) is about writing one good instruction; context engineering is about everything in the window, on every turn of the loop.

Think of the window as the model's working memory: a desk of fixed size. It is measured in tokens; in English one token is roughly ¾ of a word. Here is what competes for the desk in a typical agent:

A coding agent has a 200k-token window. Its system prompt is 3k tokens and its rules file 2k. It also has five MCP servers connected.   2. Share of the window: 60k ÷ 200k = 30%, gone before the task starts.
  3. Left for documents, tool results and conversation: 140k tokens.

More is not better: lost in the middle and context rot

If it fits, why not keep it all? Because a model's attention is spread over everything in the window. In a transformer, every token is compared with every earlier token (M1.1), so $n$ tokens make about $n^2/2$ pairs. Anthropic's post calls this an attention budget: every extra token draws on it, whether it matters or not.

Two lines of evidence show the cost:

  • Lost in the middle (Liu et al., 2023). Models answered questions from 20 retrieved documents, with the one useful document moved from first to last. Accuracy traced a U: best when it sat at the start or end, worst in the middle. For GPT-3.5-Turbo, a document in the middle was used so poorly that it scored below answering with no documents at all.
  • Context rot. A 2025 report by the vector-database company Chroma tested 18 models and found that performance became less reliable as inputs grew longer, even on simple tasks, and that similar-but-wrong “distractor” passages hurt most. The name stuck for this general effect.

Newer models handle long inputs better than 2023's did, but the advice from labs as of 2026 is the same: treat context as a finite resource with diminishing returns. Tools suffer from clutter too. Fifty overlapping tools make it harder to pick the right one than eight clear ones.

An agent's key instruction sits in the middle of a 150k-token history. What is the most likely effect?

  1. None, as long as the total is under the limit
  2. The model will refuse to answer
  3. The request fails with an error
  4. The model is more likely to overlook it than if it were near the start or end
Nothing errors: the model simply weighs the middle less well. That is why important instructions belong in the system prompt or rules file (near the start) or are restated near the end, and why trimming history helps.

Six techniques that keep context lean

The goal, in Anthropic's words, is the smallest set of high-signal tokens that gets the job done. Six habits do most of the work:

  1. Short, specific instructions. Write at the “right altitude”: clear principles and a few good examples, not pages of brittle if-this-then-that rules, and not vague slogans. Start minimal and add a line only when you see a real failure.
  2. Retrieve just in time. Don't preload every document “just in case”. Keep light references (file paths, search queries, links) and let the agent fetch the content with a tool when it needs it. Coding agents do this naturally: they search the repo and open three files rather than reading all of it.
  3. Progressive disclosure. Show a one-line summary first and the details only on demand. Agent Skills work this way, and so does on-demand tool search: in Anthropic's example, loading tool definitions only when needed cut them from about 55k to under 9k tokens.
  4. Compaction. When the window nears its limit, summarise the conversation so far (decisions, open bugs, next steps) and continue from the summary. Clearing old tool results is the lightest form: a file read twenty steps ago rarely needs to stay word for word.
  5. Structured notes outside the window. Let the agent keep a NOTES.md or a to-do file and read back only what matters. Memory files (AG.5) and the LLM wiki (AG.6) are this idea made permanent.
  6. Subagents for isolation. Hand a messy sub-task (search a huge codebase, read 40 web pages) to a subagent with its own clean window. It returns a condensed summary, often 1,000 to 2,000 tokens, instead of all the mess.

Explain like I'm 5

You're going on a hike, and your backpack is small. In front of you is a huge, messy pile: toys, books, three jumpers, a football, snacks, a map, a water bottle.

If you stuff in everything that fits, you can't find the map when you need it. So you pick the map, the water and one snack, and leave the rest at home. Smart packing isn't about carrying the most; it's about carrying the right things.

Where it breaks: a hiker feels a heavy bag, but a model doesn't “feel” clutter. It quietly does worse. And an agent can repack on the way: drop what it's done with, fetch what it needs next.

An agent must read 40 web pages to answer one research question. Which technique keeps the main agent's context cleanest?

  1. Give the reading to a subagent that returns a short summary of what it found
  2. Paste all 40 pages into the main conversation
  3. Add a rule to AGENTS.md saying “read carefully”
  4. Switch to a model with a bigger window
The subagent's window absorbs the 40 pages; the main agent sees only the condensed result. A bigger window delays the overflow but keeps all the clutter.

Prompt caching: pay once for the part that doesn't change

Every turn of an agent loop sends the whole context to the model again: system prompt, tool definitions, rules, history. Most of it is identical to last time. Prompt caching lets the provider keep its work on that identical prefix (the start of the input), so the next request can skip recomputing it.

The payoff is lower cost and a faster first token. Pricing differs by provider and changes often. As one example from 2026, Anthropic's documentation bills tokens read from its cache at a tenth of the normal input price or less, charges a little extra (1.25×) to write them, and keeps a cache entry for 5 minutes by default, refreshed each time it is used. Other providers cache automatically with their own discounts.

Caching only works on an exact prefix: change one token near the start and everything after it must be recomputed. That gives a simple layout rule:

  1. Stable things first: system prompt, tool definitions, rules files.
  2. Slowly changing things next: retrieved documents for this task, the conversation so far.
  3. The newest message last.

Small details matter. Putting today's date or a random ID at the top of the system prompt breaks the cache on every request. Tool lists should come back in the same order each time; the MCP specification (2026-07-28 revision) now asks servers to list tools in a deterministic order for exactly this reason.

In real practice: coding agents such as Claude Code, OpenAI Codex, Cursor, Gemini CLI or GitHub Copilot do most of this for you: they load rules files at the start, search files instead of reading the whole repo, compact long sessions automatically, and keep the prefix stable for caching. Your job is mostly not to undo it: keep rules files short, connect only the MCP servers you use, and start a fresh session for a new task instead of dragging an old history along.

Your app puts the current time (to the second) at the very top of its system prompt. What happens to prompt caching?

  1. Nothing; caching ignores timestamps
  2. It works better, because the prompt is more precise
  3. It breaks: the prefix changes on every request, so nothing after the timestamp can be reused
  4. Only the timestamp is cached
Caches match an exact prefix. A value that changes every request at the very top makes every prefix new. Move it to the end of the context, or drop the seconds.

Model answer: A bigger window only moves the hard limit; quality drops well before it, because attention is spread over everything and facts in the middle of long, cluttered inputs get missed (lost in the middle, context rot), and every token costs money and time. Connect to M1.1: an agent's context grows from 50k to 100k tokens. Roughly how many more token pairs must attention consider?

  1. The same number
  2. About 4 times as many
  3. About 2 times as many
  4. About 100 times as many
Attention compares each token with every earlier one, about $n^2/2$ pairs. Doubling $n$ multiplies that by $2^2 = 4$. Implementations such as FlashAttention make this fast, but the attention budget is still shared across all of it.

Which is an example of just-in-time retrieval?

  1. Pasting the whole codebase into the first message
  2. Fine-tuning the model on the documentation
  3. Listing every document's full text in the system prompt
  4. Keeping file paths in context and opening a file with a tool only when the task needs it
The agent holds light references and loads the content when it is actually needed, so the window carries only what this step uses.

An agent has worked for two hours and its window is 95% full. What does compaction do?

  1. Replaces the long history with a summary of decisions, state and next steps, then continues
  2. Deletes the system prompt to make room
  3. Compresses tokens into fewer bytes without changing what the model reads
  4. Moves the conversation to a model with a bigger window
Compaction trades the full transcript for a short, high-signal summary, freeing space while keeping what matters. Old tool results can often be dropped entirely.

For prompt caching, which order of the context is best?

  1. Newest message, then history, then system prompt
  2. Random order, so the model doesn't over-focus
  3. System prompt and tool definitions, then rules and documents, then history, then the newest message
  4. Order doesn't matter for caching
Caches reuse an exact prefix, so the stable parts go first and the fastest-changing part (the newest message) goes last.

Key takeaways

  • The context window is the model's working memory: system prompt, rules, tool definitions, documents, tool results, history and memory all compete for it.
  • Quality falls before the limit: facts in the middle get missed (Liu et al., 2023) and long, cluttered inputs make models less reliable (context rot).
  • Keep it lean: short instructions, just-in-time retrieval, progressive disclosure, compaction, notes outside the window and subagents for messy work.
  • Prompt caching makes a stable prefix cheaper and faster: stable parts first, newest message last.
